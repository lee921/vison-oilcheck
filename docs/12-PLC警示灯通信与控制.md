# 12 PLC 警示灯通信与控制

对应 PLC 协议表（本文件 §2 抄录）。实现位置（新增）：

- `tools/plc_check.py` — 只读体检工具（已完成，可在现场直接跑）
- `app/oilcheck/plc_link.py` — Modbus TCP 传输层（待实现）
- `app/oilcheck/plc_io.py` — 业务状态 → 寄存器映射与写入线程（待实现）

本文先给**实测结论**（地址通不通、从站什么脾气），再给**协议解读**（含

## 1. 地址连通性：已通

### 1.1 结论

| 检查项 | 结果 |
| --- | --- |
| ICMP `192.168.1.88` | 4/4 通，rtt 1.4~2.7 ms（avg 1.74 ms） |
| TCP `192.168.1.88:502` | 通 |
| ARP | `64:65:44:8e:ec:89`，REACHABLE |
| Modbus FC3 读保持寄存器 | 通，支持 HR0~HR19 |
| 3 分钟 / 360 次请求长稳 | 0 失败，0 重连，p50 2.6 ms、p95 3.1 ms、max 3.3 ms |

### 1.2 但不通的原因不是 PLC——是本机没有这个网段的地址

第一次测试时 `192.168.1.88` 不通，`ip route get` 显示请求被丢给默认网关
`10.3.233.254`（`eno1`）。本机原只有三个地址：

```text
eno1        10.3.233.130/24   （办公网，默认路由）
eno2         10.3.9.238/24    （相机 10.3.9.241 在这段，8000 端口通）
wlp133s0f0  10.3.34.36/24     （WiFi）
enx6c1ff7c1  —                （USB 网卡，DHCP 拿不到地址，一直"正在获取 IP"）
```

已做变更（**改了本机网络配置，请知悉**）：

```bash
nmcli connection modify "有线连接 2" \
  ipv4.method manual ipv4.addresses 192.168.1.90/24 ipv4.never-default yes
nmcli connection up     "有线连接 2"
```

`never-default yes` 保证不抢默认路由。改完 `ip route get 192.168.1.88` 走
`enx6c1ff7c17337`，PLC 立即可达。要恢复 DHCP：

```bash
nmcli connection modify "有线连接 2" ipv4.method auto ipv4.addresses "" ipv4.never-default no
nmcli connection up     "有线连接 2"
```

该连接 `autoconnect=yes`，重启后仍然是静态 `192.168.1.90`。**现场工控机
上要同样配，否则换机器又要排查一遍。**

### 1.3 同网段扫描

对 `192.168.1.1~254` 做了 ARP 扫描，**只有 `192.168.1.88` 在线**。
`cameras.json` 里登记的 2 号机 `192.168.1.65:8000` 在这段上**不存在**
（ARP INCOMPLETE，8000/80 均超时）——它要么没接在这台交换机上，要么已改
地址。这条与 PLC 无关，但顺手发现，建议现场核一下。

| 功能码 | 结果 | 解读 |
| --- | --- | --- |
| FC3 读保持寄存器 | ✓ | 唯一可用的读功能码 |
| FC1 读线圈 | exception 2 | 未实现（非法数据地址） |
| FC2 读离散输入 | exception 2 | 未实现 |
| FC4 读输入寄存器 | exception 2 | 未实现 |
| FC7 读异常状态 | exception 1 | 未实现 |
| FC8 诊断回显 | exception 1 | 未实现 |
| FC17 Report Server ID | exception 1 | 未实现 |
| FC23 读写多寄存器 | exception 1 | 未实现 |
| FC43/14 读设备标识 | exception 1 | 未实现 |
| FC6 / FC16 写 | 对越界地址返回 exception 2 | **已实现**（地址合法即可写；本次未做实际写入，见下） |

其它实测特征，直接影响控制方案：

| 特征 | 实测 |
| --- | --- |
| 地址空间 | HR0~HR19 可读，**HR20 起 exception 2**；批量一次最多 20 个（24 个报错） |
| unit id | 0 / 1 / 2 / 255 **都接受**，从站不校验。方案里仍用 1 |
| 默认值 | `HR0=0x0000`、`HR1=0x00FF`、`HR2~HR19=0` |
| 60s / 296 次轮询 + 180s / 360 次轮询 | **这些字节全程没有任何变化** |
| **并发连接** | **只允许 1 条**。持有连接 1 时，新建连接 2 连续 3 次 SYN 超时 |
| 关闭后立即重连 | 同一时刻连发的情况下第 2 次建连要等约 **1021 ms**；间隔 ≥20 ms 则 1~2 ms |
| 空闲保持 | 8s、10s、14s、16s 时仍可用；12s、18s 时读取超时 → 空闲断连点落在 **10~18s 且不稳定** |
| 断连后恢复 | 关闭后 0.1s 即可重连，建连 4 ms |

> **只允许单连接**是最要紧的一条：整台 PLC 只能有我们一个 Modbus 会话。
> 现场如果还开着博途在线监控、第三方组态或另一个脚本，会互相抢会话，
> 表现为「有时通有时超时而且是 1 秒级的超时」。排查时先确认没有别的客户端。

> 本次**没有做任何写入**。FC6/FC16 只在越界地址上试探（被 exception 2
> 拒绝，不产生写入），用来证明功能码已实现。真实写入要等字节序与位映射
> 与 PLC 侧对齐后再做，见 §5。

## 3. 协议解读

### 3.1 寄存器映射

首地址**从 0 开始**（不是 40001），端口 502，DataFormat 标注 `DCBA`。

| 地址 | 软元件 | 现场作用 | 方向 | 本方案 |
| --- | --- | --- | --- | --- |
| HR0 | VB0 | **绿通道**：bitN = 1 → 灯 N+1 绿 | 主站写入（PC → PLC） | 写 |
| HR0 | VB1 | **黄通道**：bitN = 1 → 灯 N+1 黄 | 主站写入 | 写 |
| HR1 | VB2 | **与灯无关**（实测写任何位都不动） | — | 恒写 0 |
| HR1 | VB3 | **与灯无关** | — | 恒写 0 |

> **前提：PLC 只负责显示信号，不做任何处理。** 所以运行期只写不读——不做
> 读-改-写、没有人工改判回写。

### 3.1.1 灯色编码：逐位实测结论

协议表把 VB0/VB1/VB2 解释成「运行中标记 / 良品记录 / 不良记录」，**与现场
实际不符**。用 `tools/plc_lamp_probe.py` 把 `HR0`/`HR1` 的每一位单独点亮
后，得到的真实编码是：

```text
VB0（HR0 低字节）bitN = 1  →  灯 N+1 亮绿
VB1（HR0 高字节）bitN = 1  →  灯 N+1 亮黄
同一位 VB0 与 VB1 同时为 1  →  灯 N+1 亮红      ← 红不在 HR1！
HR1（VB2/VB3）任何位       →  灯完全不动
```

实测记录（节选）：

| 写入 | 实际 |
| --- | --- |
| `HR0=0x0101`（VB0.bit0 + VB1.bit0） | 灯1 红 |
| `HR0=0x0202` … `0x8080` | 灯2 … 灯8 红 |
| `HR0=0x00FF`（VB0 全置） | 灯2~灯8 绿，灯1 灭 |
| `HR0=0xFF00`（VB1 全置） | 灯2~灯8 黄，灯1 红 |
| `HR0=0xFFFF` | 8 盏全红 |
| `HR1` 任意位 | 无反应 |

**所以「同一位置多个信号 = 红」是用 VB0+VB1 同位置双置实现的**，这也正是
现场最初的约定。

### 3.1.2 灯1 只能红，工步从灯2 起用

现场共 **8 盏灯**，但灯1 是例外：

| 写入 | 按规则应该 | 实际 |
| --- | --- | --- |
| `VB0.bit0`（`0x0001`） | 灯1 绿 | **不亮** |
| `VB1.bit0`（`0x0100`） | 灯1 黄 | **灯1 红** |

灯2~灯8 全部严格符合上节规则，只有灯1 没有绿、黄位直接红。所以**工步从
第 2 盏灯起用**（`pick=2, oiling=4`），正好是「灯2 黄 → 灯2 灯3 绿 →
灯4 黄 → 全绿 / 灯4 红」。

配置校验：`pick >= 2`、`oiling == pick + 2`、`oiling <= 8`；不满足回退默认
2/4 并记 warning（`PlcConfig.from_dict` 与 `_StepBits.from_steps` 两处）。

### 3.2 字节序：协议表的四个例子可以自证

不需要猜，协议表自己的例子就能定死：

| 行 | 例子 | 16 位值（所含寄存器） | 若「低字节 = 较小 VB 号」 |
| --- | --- | --- | --- |
| 运行中标记 | 第一步检测中 → `0000 0000 0000 0001` | 0x0001（HR0） | VB0=0x01 → 第 1 步 ✓ |
| 良品记录 | 第一步及第三步完成 → `0000 0101 0000 0000` | 0x0500（HR0） | VB1=0x05 → 第 1、3 步 ✓ |
| 不良记录 | 第一步及第三步不良 → `0000 0000 0000 0101` | 0x0005（HR1） | VB2=0x05 → 第 1、3 步 ✓ |
| 手动判断 | 第一步和第四步误判 → `0000 1001 0000 0000` | 0x0900（HR1） | VB3=0x09 → 第 1、4 步 ✓ |

四个例子全部落在「低字节是较小 VB 号」上，无一例外（已用
`tools/plc_check.py` 的 `_byte_view(order="lsb")` 逐条回归验证）。所以：

```text
HR0 = VB0 | (VB1 << 8)
HR1 = VB2 | (VB3 << 8)
```

即 **HR 的低字节 = 编号较小的 VB**。这也是 `DataFormat=DCBA` 在本项目里
的实际含义。

> 引用协议表四个例子的前提是「低字节 = 编号较小的 VB」。注意这一步在现代
> 字节序已被逐位实测确认：`VB0.bit1`（`0x0002`）点亮灯2 绿，`VB1.bit1`
> （`0x0200`）点亮灯2 黄，说明低字节 = VB0、高字节 = VB1，即 lsb 正确。
> （`byte_order` 配置项目前不参与写入，见 [13](13-审查报告.md) R38。）

### 3.3 当前值有一个现场问题

按 §3.2 的解读，当前 `HR1 = 0x00FF` 拆开是：

```text
VB2 = 0xFF  与灯无关（实测写 HR1 任何位灯都不动）
VB3 = 0x00  与灯无关
```

这 8 个 1 **不是 PLC 写的**，是上电残留（RAM 初值或以前某次调试留下）。
60 秒 + 180 秒两轮持续轮询里这 4 个字节一个都没变，说明 PLC 侧这段数据区
没有生产者，完全靠上位机驱动。

因为 `HR1` 与灯无关，**这个残留值不会让灯亮**（现场逐位实测已确认）。
上位机接上后第一帧就会写 `HR1=0x0000`。

## 4. 4 工步流程与工步位

协议是 8 个工步的流水账，本项目只有两个判定点（取料、人工二次涂油）。
现场流程定为 **4 个工步**（没有「等待涂油」这一步）:

```text
等待取料 → 取料完成 → 涂油中 → 涂油完成/异常
```

工步位（`bit(n−1)` = 第 n 盏灯）。**灯1 只能红，从灯2 起用**（`pick=2`,
`oiling=4`）：

| 状态 | 判定条件（来自 `TaskSnapshot`） | 灯1 | 灯2 | 灯3 | 灯4 | VB0（绿） | VB1（黄） | HR0 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 等待取料 | 无活动周期 | 灭 | 黄 | 灭 | 灭 | `0x00` | `0x02` | `0x0200` |
| 取料完成 | `PICKED` 且 `brush_hold_s == 0` | 灭 | 绿 | 绿 | 灭 | `0x06` | `0x00` | `0x0006` |
| 涂油中 | `PICKED` 且 `brush_hold_s > 0` | 灭 | 绿 | 绿 | 黄 | `0x06` | `0x08` | `0x0806` |
| 涂油完成（良） | `COMPLETED` | 灭 | 绿 | 绿 | 绿 | `0x0E` | `0x00` | `0x000E` |
| 涂油异常（NG） | `NG` | 灭 | 绿 | 绿 | 红 | `0x0E` | `0x08` | `0x080E` |
| 未检测 | 相机离线 / 判定报错 | 保持 | 保持 | 保持 | 保持 | 保持 | 只清纯黄 | 保持 |

**`HR1` 恒 `0x0000`** —— 它与灯完全无关（§3.1.1）。

要点：

- **红 = 同一位 VB0 和 VB1 同时置 1**，所以 NG 那盏灯的绿位也是 1
  （`VB0=0x0E` 包含灯4），黄位再置上就变红。
- **只见一个纯黄**：黄标记「正在做的那盏灯」，其余是绿或灭。
- **绿只增不减**：取料完成亮灯2、灯3 两盏绿，涂油中仍是这两盏（第 3 步
  还没完成，所以灯4 是黄），良品后灯4 也转绿。
- **掉线只清「纯黄」**：红灯是绿+黄，不能把黄位一刀切清零，否则 NG 会显示
  成良品。实现里 `vb1 = prev.vb1 & prev.vb0`，只保留红位的黄。
映射放在配置里：

```jsonc
"plc": { "steps": { "pick": 2, "oiling": 4 } }
```

> 约束是 `pick >= 2`（灯1 只能红）、`oiling == pick + 2`（取料完成亮到第
> `pick+1` 盏绿、涂油中亮到第 `oiling-1` 盏绿 + 第 `oiling` 盏黄，两者必须
> 相等才单调）、`oiling <= 8`。不满足时在配置加载与
> `_StepBits.from_steps` 两处都会回退默认 2/4 并记 warning。

## 5. 控制方案

### 5.1 分层与线程模型

```text
                         ┌────────────────────────────────────┐
station_snapshot() ─────>│ PlcEvidence （在线 + 最新周期投影）│
                         └───────────────┬────────────────────┘
                                         │
                         ┌───────────────▼────────────────────┐
                         │ PlcStepMapper （纯逻辑，无 I/O）   │
                         │  4 工步 ──> 灯色（VB0 绿/VB1 黄）   │
                         │  单件内工步单调、保持窗、补报上一件│
                         └───────────────┬────────────────────┘
                                         │ PlcFrame（不可变）
                         ┌───────────────▼────────────────────┐
                         │ PlcIoThread （独立线程，200 ms 一拍）│
                         │  值变 或 距上次写入 ≥1 s ⇒ 写       │
                         │  FC16 一次写 HR0..HR1（4 字节原子） │
                         └───────────────┬────────────────────┘
                         ┌───────────────▼────────────────────┐
                         │ PlcLink （单 socket、加锁、重连退避）│
                         └────────────────────────────────────┘
```

单拍只有**一次写**（`FC16`，2 个寄存器）；不读 PLC——PLC 只显示，不处理。

三条硬性约束：

1. **不能占用 pipeline 执行器线程**。`_process_frame` 里每帧都在跑推理，
   网络 I/O 一阻塞就直接掉帧、破坏「取料停留时长」这类时序证据；
2. **只能有一条 socket**。实测第 2 条连接必然 SYN 超时，多线程各自建连会
   把自己的会话饿死。所有请求串行化在一把锁后面；
3. **整块写**。判断结论必须一次写完 4 个字节，不能拆成多次 `FC6`——否则
   PLC 可能读到「某盏灯绿黄同时亮」这类半更新的瞬时态。

### 5.2 周期状态的映射细节

`PlcStepMapper` 内部只有 6 个字段，但有三条必须遵守的单调性规则，全部来自
现场观察：

| 规则 | 原因 |
| --- | --- |
| 同一 `task_id` 内工步只进不退 | 刷子短暂离开会让 `brush_hold_s` 回到 0，但「已经刷上了」不会撤销 |
| 收到终态后必须走完保持窗，哪怕下一件已经来了 | 提前切工步 2 会让上一件的结论被新件清零覆盖，PLC 来不及读 |
| 保持窗结束后这一件不再触发工步 4 | `pipeline._cleanup` 按条数保留结束周期，它会继续留在快照里 |

另外有一条**补报**规则，这是离线回放实测出来的：

```text
工步3 涂油中 → (T1 被判 NG 的同时 T2 已开始取料) → 工步2 取料完成
                                    ↑ 200ms 轮询很容易跨过这一帧
```

漏涂的主要路径是被下一次取料顶掉（`_supersede_unfinished`）。若直接按
当前证据切工步 2，上一件的 **NG 永远写不进 PLC**。所以证据里额外带
`superseded_task_id`：发现「上一件刚判终态、当前已是新件」时，先补报上一件
的工步 4（NG），同样走保持窗，之后再进新件的工步 2。

`tools/plc_dryrun.py` 回放三段示例视频可复现这个序列。

### 5.3 灯色随工步推进

只有 `HR0` 驱动灯，按工步走（灯1 不用）：

| 事件 | 灯2 | 灯3 | 灯4 | VB0（绿） | VB1（黄） | HR0 |
| --- | --- | --- | --- | --- | --- | --- |
| 等待取料 | 黄 | 灭 | 灭 | `0x00` | `0x02` | `0x0200` |
| 取料确认 | 绿 | 绿 | 灭 | `0x06` | `0x00` | `0x0006` |
| 涂油中 | 绿 | 绿 | 黄 | `0x06` | `0x08` | `0x0806` |
| 二次涂油完成 | 绿 | 绿 | 绿 | `0x0E` | `0x00` | `0x000E` |
| 漏涂 NG | 绿 | 绿 | **红** | `0x0E` | `0x08` | `0x080E` |

绿是累计位，所以 PLC 数绿灯个数就知道这一件做到第几步；黄只亮一盏（正在
做的那盏灯）；红只出现在漏涂那盏灯，由绿+黄同位置双置实现。`HR1` 恒 0。
完整推导见 §4。

### 5.4 手动良品判断（VB3）

**本方案不使用。** PLC 只负责显示，不提供人工改判输入，所以 VB3 恒写 0，
也不读。好处是没有 `HR1` 的读-改-写，不存在 PC 与 PLC 互相覆盖的竞态。

人工改判走软件侧的复核页（`ui/pages/review_page.py`），改判结果写进事件
JSONL，与 PLC 无关。

> 若将来 PLC 侧确实要启用 VB3 输入，必须先把写入路径改成「先读 HR1 →
> 处理 VB3 的位 → 再写回」，并且把 VB3 挪到独立寄存器更稳（它现在与 VB2
> 共用 HR1）。

### 5.5 启动连通性检测

**每次启动都会自动测一次 PLC 通不通**，结果写进日志与监控页芯片。

| 时机 | 行为 |
| --- | --- |
| `PlcIoThread.start()` | 起线程后、进入主循环前立刻做一次 `建连 + FC3 读 HR0..HR1` |
| 成功 | 日志 `PLC 启动检测通过：192.168.1.88:502 可读，HR0=... HR1=...`；芯片显示 `PLC：在线 · 工步N` |
| 成功之后 | **立刻主动写一次「等待取料」帧**（灯2 黄，`HR0=0x0200 HR1=0x0000`），把状态确定下来 |
| 失败 | 日志 WARNING 带原因（超时/被占用/网段不对）；芯片显示红色 `PLC：启动检测失败`，悬停看原因 |
| 只读联调（`dry_run`） | **同样检测**，但**不写**——压残留值也跳过 |
| 服务启动 | **不阻塞、不阻止**：检测跑在 PLC 线程里（`start()` 实测 0 ms 返回），失败时视觉检测照常运行，PLC 线程按退避继续重连 |

### 5.5.1 启动为什么先写一次「等待取料」

该 PLC 上电后这段数据区是 `HR1=0x00FF`。虽然它**与灯无关**（§3.1.1 实测
确认），但留着上位机上一次的旧值总不如主动写一次明确状态。不主动覆盖的话，现场从开机到主循环第一拍（最多 200 ms）
之间会看到三红；虽然很短，但 PLC 侧按 `hold_s` 之类节拍读的话可能正好读到。

所以启动检测通过后、进主循环前先写一次 `等待取料`（`HR0=0x0200`）：
灯2 亮黄、`HR1` 清零，状态立即确定。代码在
`PlcIoThread._run()` → `_prime_idle_frame()`，映射值由
`PlcStepMapper.prime_idle()` 给出（它同时把映射状态重置为初始态）。

只在**非只读 + 检测通过**时写。检测失败时不硬写，交给主循环按退避重连，
再靠「值变立即写 / 1 s 无条件重写」补上——效果一样，只是晚一点。

为什么不用同步检测：`OilCheckService.start()` 在 UI 线程上调用，同步建连
最坏要等一个 `connect_timeout_s`（默认 1 s），开机时会明显感觉界面卡一下。
放进线程既满足「启动就检测」，又不影响启动速度。

结果字段（`service.plc_status()` / 芯片 tooltip）：

| 字段 | 含义 |
| --- | --- |
| `startup_ok` | `True` 通过 / `False` 失败 / `null` 还没测完或未启用 |
| `startup_message` | 成功时带读到的寄存器值；失败时带具体原因 |

手动复测：设置页「PLC 警示灯」里的**测试连接**按钮，或跑
`tools/plc_check.py`——两者都是纯读，不改 PLC 状态。

### 5.6 写入节奏与自愈

| 场景 | 动作 |
| --- | --- |
| 线程启动（检测通过） | 先写一次「等待取料」压掉残留值（§5.5.1） |
| 期望值变化 | 立即写（延迟 ≤ 一拍，约 200 ms） |
| 期望值不变 | 每 1 s **无条件重写一次** |
| 重连成功 | 立即写一次完整值 |
| PLC 重启 / 内存复位 | 由「1 s 无条件重写」自愈，最多晚 1 s（三红最多存在 1 s） |

不做无条件重写的话，PLC 一重启这段数据区就回到 `0x00FF` 那种残留态，
而视觉侧「值没变、不用写」，两边会一直不一致，现场表现为「灯的状态跟
界面不对应」。1 s 一次的重写代价可以忽略（实测 2.6 ms/次）。

### 5.7 链路失效

| 情况 | 行为 |
| --- | --- |
| 请求超时 | 立即判链路断，关 socket，进重连退避 |
| 退避序列 | 200 / 500 / 1000 / 2000 / 5000 ms，成功后复位 |
| 重连后 | 立即写一次完整帧（不依赖「值变才写」） |
| 期间产生的结论 | 映射层照常推进；重连后写入的是**当前**工步，不补历史帧 |
| 视觉链路 | **完全不受影响**，事件照常入库 |

「只写当前工步、不补历史」是有意的取舍：PLC 只显示，断链期间那一件的
中间过程对操作员已经失去意义，补一串过期帧反而会把工步号刷乱。
唯一的例外是 §5.2 的**上一件结论补报**——那条在映射层完成，不依赖重连。

实测支撑这些参数：断连后 0.1 s 即可重连（建连 4 ms）；但同一时刻连发
的第二次建连要等约 1021 ms，所以退避从 200 ms 起就够了，不要 0 ms 猛重试。

### 5.8 保活

PLC 空闲 10~18 s 会断连，且**断得不干净**——socket 不会收到 FIN，下一
次写入才表现为超时。因此：

- 心跳就是「每 1 s 无条件重写一次」（`refresh_interval_s`），远小于 10 s，
  连接一直在忙；
- 请求超时设 `500 ms`（实测 p95 3.1 ms，500 ms 有 160 倍余量）；
- 任何一次写超时都当成断链，直接重连，不做「再试一次」——PLC 单会话，
  留着半死连接会挡住新连接。

### 6.0.1 灯色探针（唯一需要人看的工具）

代码只能保证「写进 PLC 的字节是对的」；**字节到灯色的最后一段在 PLC 侧**。
如果现场看到的颜色与 §4 的表不符（例如「等待取料」亮红而不是黄），说明
这一段的假设有问题，可能是字节序、灯与位的对应关系、或红灯另有条件。
这时改用探针，一帧只写一种颜色一盏灯，由现场人员直接看灯：

```bash
# 先关掉主程序（该 PLC 只允许一条 Modbus 会话）
uv run python tools/plc_lamp_probe.py --yes
uv run python tools/plc_lamp_probe.py --yes --only base --hold 4
```

它会依次写「绿·灯1/2/3」「黄·灯1/2/3」「红·灯1/2/3」「同位置绿+黄」等候选值，
每行先打印协议预期，停留 `--hold` 秒让你核对，结束时**写回原值**。工具输出
末尾给了对照结论表（灯号反了 / 字节序反了 / 红灯另有条件 / 红色是默认态），
按实际看到的现象对号入座。

> 探针会真实写入 PLC 数据区，所以要求显式 `--yes`，并且必须先停主程序。

## 7. 待确认清单（必须先答再上生产）

按重要性排序。前 3 条不确认就开写，风险是「把良品写成不良」或「写出去
没人认」。

1. **谁负责清零绿灯/红灯？**
   本方案由 PC 在保持窗结束时（回工步 1 的同一次写入）整块清零，PLC 只读。
   需要 PLC 侧确认它**不会**也去清——两边都清会互相覆盖，表现为第二件带着
   第一件的位或读到半清数据。**这是方案里唯一没有实证的功能缺口。**

2. **PLC 怎么知道「本件的记录已经完整」？**
   现在只有 4 个字节、没有「数据有效」握手位。我们靠 FC16 原子写保证
   PLC 不会读到半更新，但「一件是否已经判完」PLC 无从判断。建议 PLC 侧
   增加一个握手位，或由 PLC 按节拍（工件到位/离开）自行裁决。

3. **验收时逐状态核对灯色**：编码已由 `tools/plc_lamp_probe.py` 逐位实测
   确定（§3.1.1），但仍建议在四个工步各看一次实际灯色，确认与 §4 的表一致。

4. **掉线怎么显示？** 三个字节已被三种颜色占满，没有剩余位做「上位机
   离线」指示。当前实现是掉线只灭黄灯、绿/红保持结论（见 §4）。若现场
   要求「掉线一眼可见」，需要另定输出地址。

5. **确认 PLC 侧不会往 VB3 写任何东西。** 本方案只写不读 VB3（恒置 0）；
   若 PLC 实际会写它，方案必须改成读-改-写。

6. **通信心跳位**：上位机死掉时 PLC 无法感知（协议里没有心跳）。目
   前只能靠「黄灯全灭」这一个弱信号。要不要约定一个 500 ms 翻转的心跳位？

7. `192.168.1.65`（2 号机）为什么不在线？是否已改址或未接入本交换机。

## 8. 联调与验收步骤

| 步 | 内容 | 通过标准 |
| --- | --- | --- |
| 1 | `tools/plc_check.py` | 全绿（本机已绿） |
| 2 | 开 `dry_run=false` 后看灯 | 空闲时 **灯2 黄**，`HR0=0x0200` |
| 3 | 开 `dry_run=true`，跑一个班次 | 日志里的期望值序列与 PLC 在线监视逐位一致 |
| 4 | 重启程序 | 日志出现「PLC 启动检测通过」；拔掉网线重启应出现「启动检测失败」且视觉检测照常跑 |
| 5 | `tools/plc_dryrun.py` 回放示例视频 | 打印的序列与 §4 表格一致，含「上一件被顶掉时补报 NG」 |
| 6 | `dry_run=false`，跑一件正常件 | 灯2~灯4 依次 `黄灭灭 → 绿绿灭 → 绿绿黄 → 绿绿绿`；HR0 依次 `0x0200→0x0006→0x0806→0x000E`，HR1 恒 0 |
| 7 | 制造一件漏涂 | 结束时灯4 红：VB0=`0x0E`、VB1=`0x08`、HR0=`0x080E`，HR1 恒 0 |
| 8 | 断链 5 min | 视觉不中断；重连后补写正确、无重复写 |
| 9 | PLC 断电重启 | 运行中：≤1 s 内被「无条件重写」自愈；程序重启：启动检测通过后立即写「等待取料」，三红在进主循环前就消失 |
| 10 | 连续 8 h | 写失败 0，连接重连 ≤3 次，无视觉掉帧 |

第 2 步不通过就停，不要往下走。
