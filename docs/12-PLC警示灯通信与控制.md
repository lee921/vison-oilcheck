## 1. 地址连通性：已通

### 1.1 结论

| 检查项 | 结果 |
| --- | --- |
| ICMP `192.168.1.88` | 4/4 通，rtt 1.4~2.7 ms（avg 1.74 ms） |
| TCP `192.168.1.88:502` | 通 |
| ARP | `64:65:44:8e:ec:89`，REACHABLE |
| Modbus FC3 读保持寄存器 | 通，支持 HR0~HR19 |
| 3 分钟 / 360 次请求长稳 | 0 失败，0 重连，p50 2.6 ms、p95 3.1 ms、max 3.3 ms |

### 1.2 但不通的原因不是 PLC——是本机没有这个网段的地址

第一次测试时 `192.168.1.88` 不通，`ip route get` 显示请求被丢给默认网关
`10.3.233.254`（`eno1`）。本机原只有三个地址：

```text
eno1        10.3.233.130/24   （办公网，默认路由）
eno2         10.3.9.238/24    （相机 10.3.9.241 在这段，8000 端口通）
wlp133s0f0  10.3.34.36/24     （WiFi）
enx6c1ff7c1  —                （USB 网卡，DHCP 拿不到地址，一直"正在获取 IP"）
```

已做变更（**改了本机网络配置，请知悉**）：

```bash
nmcli connection modify "有线连接 2" \
  ipv4.method manual ipv4.addresses 192.168.1.90/24 ipv4.never-default yes
nmcli connection up     "有线连接 2"
```

`never-default yes` 保证不抢默认路由。改完 `ip route get 192.168.1.88` 走
`enx6c1ff7c17337`，PLC 立即可达。要恢复 DHCP：

```bash
nmcli connection modify "有线连接 2" ipv4.method auto ipv4.addresses "" ipv4.never-default no
nmcli connection up     "有线连接 2"
```

该连接 `autoconnect=yes`，重启后仍然是静态 `192.168.1.90`。**现场工控机
上要同样配，否则换机器又要排查一遍。**

### 1.3 同网段扫描

对 `192.168.1.1~254` 做了 ARP 扫描，**只有 `192.168.1.88` 在线**。
`cameras.json` 里登记的 2 号机 `192.168.1.65:8000` 在这段上**不存在**
（ARP INCOMPLETE，8000/80 均超时）——它要么没接在这台交换机上，要么已改
地址。这条与 PLC 无关，但顺手发现，建议现场核一下。

| FC1 读线圈 | exception 2 | 未实现（非法数据地址） |
| FC2 读离散输入 | exception 2 | 未实现 |
| FC4 读输入寄存器 | exception 2 | 未实现 |
| FC7 读异常状态 | exception 1 | 未实现 |

| FC17 Report Server ID | exception 1 | 未实现 |

| FC43/14 读设备标识 | exception 1 | 未实现 |
| FC6 / FC16 写 | 对越界地址返回 exception 2 | **已实现**（地址合法即可写；本次未做实际写入，见下） |

其它实测特征，直接影响控制方案：

| 特征 | 实测 |
| --- | --- |
| 地址空间 | HR0~HR19 可读，**HR20 起 exception 2**；批量一次最多 20 个（24 个报错） |
| unit id | 0 / 1 / 2 / 255 **都接受**，从站不校验。方案里仍用 1 |
| 默认值 | `HR0=0x0000`、`HR1=0x00FF`、`HR2~HR19=0` |
| 60s / 296 次轮询 + 180s / 360 次轮询 | **这些字节全程没有任何变化** |
| **并发连接** | **只允许 1 条**。持有连接 1 时，新建连接 2 连续 3 次 SYN 超时 |
| 关闭后立即重连 | 同一时刻连发的情况下第 2 次建连要等约 **1021 ms**；间隔 ≥20 ms 则 1~2 ms |
| 空闲保持 | 8s、10s、14s、16s 时仍可用；12s、18s 时读取超时 → 空闲断连点落在 **10~18s 且不稳定** |
| 断连后恢复 | 关闭后 0.1s 即可重连，建连 4 ms |

> **只允许单连接**是最要紧的一条：整台 PLC 只能有我们一个 Modbus 会话。
> 现场如果还开着博途在线监控、第三方组态或另一个脚本，会互相抢会话，
> 表现为「有时通有时超时而且是 1 秒级的超时」。排查时先确认没有别的客户端。

> 本次**没有做任何写入**。FC6/FC16 只在越界地址上试探（被 exception 2
> 拒绝，不产生写入），用来证明功能码已实现。真实写入要等字节序与位映射
> 与 PLC 侧对齐后再做，见 §5。

## 3. 协议解读

### 3.1 寄存器映射

首地址**从 0 开始**（不是 40001），端口 502，DataFormat 标注 `DCBA`。

| 地址 | 软元件 | 功能 | 方向 | 本方案 |
| --- | --- | --- | --- | --- |
| HR0 | VB0 | 8 位运行中标记 | 主站写入（PC → PLC） | 写 |
| HR0 | VB1 | 8 位良品数据记录 | 主站写入 | 写 |
| HR1 | VB2 | 8 位不良数据记录 | 主站写入 | 写 |
| HR1 | VB3 | 8 位手动良品判断 | 主站读写（PLC 写、PC 读后清） | **恒写 0，不读** |

> **前提：PLC 只负责显示信号，不做任何处理。** 所以运行期只写不读——不读
> VB3、不做读-改-写、没有人工改判回写。若将来 PLC 侧启用 VB3 输入，必须
> 先改成读-改-写（VB3 与 VB2 共用 HR1）。

每个字节 8 位，对应 8 个工步，**bit(n−1) = 第 n 步**。

### 3.2 字节序：协议表的四个例子可以自证

不需要猜，协议表自己的例子就能定死：

| 行 | 例子 | 16 位值（所含寄存器） | 若「低字节 = 较小 VB 号」 |
| --- | --- | --- | --- |
| 运行中标记 | 第一步检测中 → `0000 0000 0000 0001` | 0x0001（HR0） | VB0=0x01 → 第 1 步 ✓ |
| 良品记录 | 第一步及第三步完成 → `0000 0101 0000 0000` | 0x0500（HR0） | VB1=0x05 → 第 1、3 步 ✓ |
| 不良记录 | 第一步及第三步不良 → `0000 0000 0000 0101` | 0x0005（HR1） | VB2=0x05 → 第 1、3 步 ✓ |
| 手动判断 | 第一步和第四步误判 → `0000 1001 0000 0000` | 0x0900（HR1） | VB3=0x09 → 第 1、4 步 ✓ |

四个例子全部落在「低字节是较小 VB 号」上，无一例外（已用
`tools/plc_check.py` 的 `_byte_view(order="lsb")` 逐条回归验证）。所以：

```text
HR0 = VB0 | (VB1 << 8)
HR1 = VB2 | (VB3 << 8)
```

即 **HR 的低字节 = 编号较小的 VB**。这也是 `DataFormat=DCBA` 在本项目里
的实际含义。

> 仍需一次现场确认：请 PLC 侧**只**置「第一步运行中标记」，读 HR0。
> 期望 `HR0 = 0x0001`。若读到 `0x0100`，说明上表全部反过来，此时必须
> 停止联调、改回按高字节解读。这一步只要 30 秒，一定要做。

### 3.3 当前值有一个现场问题

按 §3.2 的解读，当前 `HR1 = 0x00FF` 拆开是：

```text
VB2 = 0xFF  不良数据记录 = 8 个工步全部不良
VB3 = 0x00  手动良品判断 = 无
```

而 VB2 是「主站写入」——也就是说这 8 个 1 **不是 PLC 写的**，是上电残留
（RAM 初值或以前某次调试留下）。同时 60 秒 + 180 秒两轮持续轮询里这 4 个
字节**一个都没变**，说明 PLC 侧的这段数据区目前没有生产者，完全靠上位机
驱动，与「主站写入」的方向一致。

风险很直白：**如果警示灯直接由「不良数据记录」驱动，那么 PLC 现在就在
报 8 步全不良**。现场请立刻看一眼灯的实际状态。上位机接上后第一帧就会
用真实结果覆盖它；但在上位机上线之前，这个残留值需要 PLC 侧清零或人工确认。

## 4. 4 工步流程与工步位

协议是 8 个工步的流水账，本项目只有两个判定点（取料、人工二次涂油）。
现场流程定为 **4 个工步**（没有「等待涂油」这一步）:

```text
等待取料 → 取料完成 → 涂油中 → 涂油完成/异常
```

工步位（`bit(n−1) = 第 n 步`）:

| 状态 | 判定条件（来自 `TaskSnapshot`） | VB0 | VB1 | VB2 |
| --- | --- | --- | --- | --- |
| 等待取料 | 无活动周期 | `0b0001` | `0b0000` | `0` |
| 取料完成 | `PICKED` 且 `brush_hold_s == 0` | `0b0010` | `0b0001` | `0` |
| 涂油中 | `PICKED` 且 `brush_hold_s > 0` | `0b0100` | `0b0011` | `0` |
| 涂油完成（良） | `COMPLETED` | `0b0000` | `0b0111` | `0` |
| 涂油异常（NG） | `NG` | `0b0000` | `0b0011` | `0b0100` |
| 未检测 | 相机离线 / 判定报错 | `0x00` | 保持 | 保持 |

`HR0 = VB0 | (VB1 << 8)`，`HR1 = VB2`（VB3 恒 0）。

要点：

三条语义约定：

- **VB0 = 正在检测的工步位。** 判定结束后不再是任何一步，所以涂油完成/异常
  时 `VB0 = 0b0000`——表示「这一件已出结论」，而**不是**「上位机掉线」。
  掉线也写 0，两者靠 VB1/VB2 是否已有第 3 步结论区分。
- **VB1 = 已通过的工步累计位。** 取料完成置第 1 位（`0b0001`）；涂油中
  前两步已过（`0b0011`）；良品完成三步全过（`0b0111`）。
- **VB2 = 失败的那一步位。** 只有漏涂时置第 3 位（`0b0100`），此时 VB1 停在
  `0b0011`（前两步已通过）。

结论在 PLC 上保持 `hold_s`（默认 1 s，墙钟计时），给 PLC 读走。
保持窗结束后回等待取料，**同一次写入把 VB1/VB2 清零**（新件清零）。
- 「等待取料」只能由「无活动周期」表达：`TaskStage.WAITING_PICK` 在运行期
  不会停留（`_ensure_cycle` 建完立刻转 `PICKED`）。
- 相机离线只清 VB0，VB1/VB2 保持——PC 掉线不该抹掉已写出的记录。

映射放在配置里，现场改工步号不用改代码：

```jsonc
"plc": { "steps": { "pick": 1, "oiling": 3 } }
```

> 协议表自己的例子用到「第一步及第三步」「第一步和第四步」。如果现场实际
> 不是 1/3，改这两个数字即可，代码里 `pick`/`oiling` 都支持 1~8；VB1 的
> 累计位会按配置的工步号自动算。

## 5. 控制方案

### 5.1 分层与线程模型

```text
                         ┌────────────────────────────────────┐
station_snapshot() ─────>│ PlcEvidence （在线 + 最新周期投影）│
                         └───────────────┬────────────────────┘
                                         │
                         ┌───────────────▼────────────────────┐
                         │ PlcStepMapper （纯逻辑，无 I/O）   │
                         │  4 工步 ──> 期望 VB0/VB1/VB2       │
                         │  单件内工步单调、保持窗、补报上一件│
                         └───────────────┬────────────────────┘
                                         │ PlcFrame（不可变）
                         ┌───────────────▼────────────────────┐
                         │ PlcIoThread （独立线程，200 ms 一拍）│
                         │  值变 或 距上次写入 ≥1 s ⇒ 写       │
                         │  FC16 一次写 HR0..HR1（4 字节原子） │
                         └───────────────┬────────────────────┘
                         ┌───────────────▼────────────────────┐
                         │ PlcLink （单 socket、加锁、重连退避）│
                         └────────────────────────────────────┘
```

单拍只有**一次写**（`FC16`，2 个寄存器）；不读 PLC——PLC 只显示，不处理。

三条硬性约束：

1. **不能占用 pipeline 执行器线程**。`_process_frame` 里每帧都在跑推理，
   网络 I/O 一阻塞就直接掉帧、破坏「取料停留时长」这类时序证据；
2. **只能有一条 socket**。实测第 2 条连接必然 SYN 超时，多线程各自建连会
   把自己的会话饿死。所有请求串行化在一把锁后面；
3. **整块写**。判断结论必须一次写完 4 个字节，不能拆成多次 `FC6`——否则
   PLC 可能读到「良品=1 且不良=0」的瞬时态。

### 5.2 周期状态的映射细节

`PlcStepMapper` 内部只有 6 个字段，但有三条必须遵守的单调性规则，全部来自
现场观察：

| 规则 | 原因 |
| --- | --- |
| 同一 `task_id` 内工步只进不退 | 刷子短暂离开会让 `brush_hold_s` 回到 0，但「已经刷上了」不会撤销 |
| 收到终态后必须走完保持窗，哪怕下一件已经来了 | 提前切工步 2 会让上一件的结论被新件清零覆盖，PLC 来不及读 |
| 保持窗结束后这一件不再触发工步 4 | `pipeline._cleanup` 按条数保留结束周期，它会继续留在快照里 |

另外有一条**补报**规则，这是离线回放实测出来的：

```text
工步3 涂油中 → (T1 被判 NG 的同时 T2 已开始取料) → 工步2 取料完成
                                    ↑ 200ms 轮询很容易跨过这一帧
```

漏涂的主要路径是被下一次取料顶掉（`_supersede_unfinished`）。若直接按
当前证据切工步 2，上一件的 **NG 永远写不进 PLC**。所以证据里额外带
`superseded_task_id`：发现「上一件刚判终态、当前已是新件」时，先补报上一件
的工步 4（NG），同样走保持窗，之后再进新件的工步 2。

`tools/plc_dryrun.py` 回放三段示例视频可复现这个序列。

### 5.3 良品 / 不良记录（VB1 / VB2）

VB1 是累计式写法，所以「第 n 步良品」= 第 1..n 位全为 1：

| 事件 | VB1（已通过） | VB2（失败步） |
| --- | --- | --- |
| 取料确认 | `0b0001` | `0` |
| 涂油中 | `0b0011` | `0` |
| 二次涂油完成 | `0b0111` | `0` |
| 漏涂 NG | `0b0011` | `0b0100` |

与协议「对应步骤良品则将对应位置 1」一致：PLC 数 VB1 里连续 1 的个数就知道
这一件做到第几步。

### 5.4 手动良品判断（VB3）

**本方案不使用。** PLC 只负责显示，不提供人工改判输入，所以 VB3 恒写 0，
也不读。好处是没有 `HR1` 的读-改-写，不存在 PC 与 PLC 互相覆盖的竞态。

人工改判走软件侧的复核页（`ui/pages/review_page.py`），改判结果写进事件
JSONL，与 PLC 无关。

> 若将来 PLC 侧确实要启用 VB3 输入，必须先把写入路径改成「先读 HR1 →
> 处理 VB3 的位 → 再写回」，并且把 VB3 挪到独立寄存器更稳（它现在与 VB2
> 共用 HR1）。

### 5.5 启动连通性检测

**每次启动都会自动测一次 PLC 通不通**，结果写进日志与监控页芯片。

| 时机 | 行为 |
| --- | --- |
| `PlcIoThread.start()` | 起线程后、进入主循环前立刻做一次 `建连 + FC3 读 HR0..HR1` |
| 成功 | 日志 `PLC 启动检测通过：192.168.1.88:502 可读，HR0=... HR1=...`；芯片显示 `PLC：在线 · 工步N` |
| 失败 | 日志 WARNING 带原因（超时/被占用/网段不对）；芯片显示红色 `PLC：启动检测失败`，悬停看原因 |
| 只读联调（`dry_run`） | **同样检测**——读不需要权限，现场开机就想知道通不通 |
| 服务启动 | **不阻塞、不阻止**：检测跑在 PLC 线程里（`start()` 实测 0 ms 返回），失败时视觉检测照常运行，PLC 线程按退避继续重连 |

为什么不用同步检测：`OilCheckService.start()` 在 UI 线程上调用，同步建连
最坏要等一个 `connect_timeout_s`（默认 1 s），开机时会明显感觉界面卡一下。
放进线程既满足「启动就检测」，又不影响启动速度。

结果字段（`service.plc_status()` / 芯片 tooltip）：

| 字段 | 含义 |
| --- | --- |
| `startup_ok` | `True` 通过 / `False` 失败 / `null` 还没测完或未启用 |
| `startup_message` | 成功时带读到的寄存器值；失败时带具体原因 |

手动复测：设置页「PLC 警示灯」里的**测试连接**按钮，或跑
`tools/plc_check.py`——两者都是纯读，不改 PLC 状态。

### 5.6 写入节奏与自愈

| 场景 | 动作 |
| --- | --- |
| 期望值变化 | 立即写（延迟 ≤ 一拍，约 200 ms） |
| 期望值不变 | 每 1 s **无条件重写一次** |
| 重连成功 | 立即写一次完整值 |
| PLC 重启 / 内存复位 | 由「1 s 无条件重写」自愈，最多晚 1 s |

不做无条件重写的话，PLC 一重启这段数据区就回到 `0x00FF` 那种残留态，
而视觉侧「值没变、不用写」，两边会一直不一致，现场表现为「灯的状态跟
界面不对应」。1 s 一次的重写代价可以忽略（实测 2.6 ms/次）。

### 5.7 链路失效

| 情况 | 行为 |
| --- | --- |
| 请求超时 | 立即判链路断，关 socket，进重连退避 |
| 退避序列 | 200 / 500 / 1000 / 2000 / 5000 ms，成功后复位 |
| 重连后 | 立即写一次完整帧（不依赖「值变才写」） |
| 期间产生的结论 | 映射层照常推进；重连后写入的是**当前**工步，不补历史帧 |
| 视觉链路 | **完全不受影响**，事件照常入库 |

「只写当前工步、不补历史」是有意的取舍：PLC 只显示，断链期间那一件的
中间过程对操作员已经失去意义，补一串过期帧反而会把工步号刷乱。
唯一的例外是 §5.2 的**上一件结论补报**——那条在映射层完成，不依赖重连。

实测支撑这些参数：断连后 0.1 s 即可重连（建连 4 ms）；但同一时刻连发
的第二次建连要等约 1021 ms，所以退避从 200 ms 起就够了，不要 0 ms 猛重试。

### 5.8 保活

PLC 空闲 10~18 s 会断连，且**断得不干净**——socket 不会收到 FIN，下一
次写入才表现为超时。因此：

- 心跳就是「每 1 s 无条件重写一次」（`refresh_interval_s`），远小于 10 s，
  连接一直在忙；
- 请求超时设 `500 ms`（实测 p95 3.1 ms，500 ms 有 160 倍余量）；
- 任何一次写超时都当成断链，直接重连，不做「再试一次」——PLC 单会话，
  留着半死连接会挡住新连接。

## 7. 待确认清单（必须先答再上生产）

按重要性排序。前 3 条不确认就开写，风险是「把良品写成不良」或「写出去
没人认」。

1. **谁负责清 VB1/VB2？**
   本方案由 PC 在保持窗结束时（回工步 1 的同一次写入）整块清零，PLC 只读。
   需要 PLC 侧确认它**不会**也去清——两边都清会互相覆盖，表现为第二件带着
   第一件的位或读到半清数据。**这是方案里唯一没有实证的功能缺口。**

2. **PLC 怎么知道「本件的 8 步记录已经完整」？**
   现在只有 4 个字节、没有「数据有效」握手位。我们靠 FC16 原子写保证
   PLC 不会读到半更新，但「一件是否已经判完」PLC 无从判断。建议 PLC 侧
   增加一个握手位，或由 PLC 按节拍（工件到位/离开）自行裁决。

3. **第几步 = 取料、第几步 = 二次涂油？**（§4，默认 1 / 4）

4. **警示灯到底由谁驱动？**
   这 4 个字节是「数据记录」，不是「灯的输出」。灯要么由 PLC 内部逻辑
   从这些字节推导，要么另有输出寄存器。若是后者，请给出灯的控制地址与
   真值表（红/黄/绿各自对应什么条件、是否闪、闪频）。

5. **确认 PLC 侧不会往 VB3 写任何东西。** 本方案只写不读 VB3（恒置 0）；
   若 PLC 实际会写它，方案必须改成读-改-写。

6. **通信心跳位**：上位机死掉时 PLC 无法感知（协议里没有心跳）。目
   前只能靠「运行中标记全部为 0」这一个弱信号。要不要约定一个 500 ms
   翻转的心跳位？

7. `192.168.1.65`（2 号机）为什么不在线？是否已改址或未接入本交换机。
