# 14 NG 事件片段存储设计

实现位置：新增 `app/oilcheck/clips.py`，改 `app/oilcheck/service.py` 与
`app/oilcheck/events.py`；UI 侧 `ui/pages/review_page.py` 已有入口。

## 1. 目标与范围

复核员看到一条 `OILING_MISSING`（漏涂 NG）时，要能**直接播放这一件前后的画面**，
而不是去几个小时长的训练录像里翻。

范围：

- 只对**需要人工复核**的事件存片段：`result == NEEDS_REVIEW`，当前就是
  `OILING_MISSING`（漏涂）。`PICK` / `MANUAL_OILING` 是确认事件，不存。
- 片段是**相机原始画面**，不叠 ROI/检测框（与训练录制一致）。
- 只对实时相机生效。示例回放（`video_source` 非空）不存：回放没有现场价值，
  而且回放时文件本来就在。

不在范围内：

- 不做逐帧标注、不写训练用元数据；
- 不做自动清理以外的磁盘配额管理（只保留天数 + 每件上限）。

## 1.1 片段覆盖的完整过程

**从取料前 1.5 秒开始，到判出涂油 NG 后 1.5 秒结束。**

```
取料 ──[等满 oiling_timeout_s＝5s]──▶ 判出 NG ──1.5s──▶ 片段结束
  ▲
  └── 1.5s ──▶ 片段开始
```

也就是说片段里包含：伸手 → 取走杆 → 那 5 秒里没人来涂油 → 判出 NG 后
再 1.5 秒的现场反应。**中间那 5 秒等待不裁**——它是「漏涂」这件事本身。

## 2. 为什么不能「收到事件再开始录」

NG 是**事后**才成立的事实。`OILING_MISSING` 的两个触发点都晚于事发：

| 触发 | 时刻 | 需要回看的起点 |
| --- | --- | --- |
| `oiling_timeout` | 取料后 `oiling_timeout_s`（默认 5s） | 取料那一刻（`picked_at`） |
| `superseded_by_pick` | **下一次**取料确认时 | 上一件取料那一刻 |

等事件回调才开始写，前面那 10 秒已经过去了。所以必须先有**环形缓冲**。

## 3. 总体结构

```text
OilCheckService 轮询线程（每帧）
  │
  ├─ recorder.submit()                   训练录制（原样）
  │
  └─ clip_service.push(camera_id, Frame)   ← 新增：每帧进环形缓冲
        │
        └─ 每相机一个 _ClipBuffer
              deque[(ts, bgr)]，容量 = pre_seconds × fps
              只保留 unconsumed，超出容量丢最旧

判定线程 _process_frame
  │
  └─ pipeline.process() ──on_event──► OilCheckService._on_event
                                          │
                                          ├─ event_store.add()（原样）
                                          └─ clip_service.on_event(event, now_ts)
                                                │  ★ 关键：事件同步回调，
                                                │  此刻缓冲里还是「事件时刻 − pre_seconds」
                                                │  到「事件时刻」的画面
                                                ▼
                                          登记一个 _PendingClip
                                          （事件、起点帧、键）

OilCheckService 轮询线程（后续帧）
  │
  └─ clip_service.push() 内部顺带推进已登记的 _PendingClip：
        条件成立时把帧交给写盘线程（_ClipWriter，独立线程）

_ClipWriter 线程
  │
  └─ imdecode → VideoWriter.write → 写元数据 → 回调回填事件
```

### 3.1 为什么状态放在 `_on_event` 里定，帧放在轮询线程里攒

`_on_event` 由判定线程在 `pipeline.process()` 内部同步调用，那一刻的
`self._last_detections` / 当前帧仍然有效，而且**缓冲里最后几帧正好是事件时刻的画面**。
把「这次要录哪一段」在这里一次性定下来，最不容易错位。

写盘既不能放在判定线程，也**不能放在轮询线程**：

- 判定线程：`cv2.VideoWriter` 编码是同步的，一段 15 秒的片段能卡住判定
  几百毫秒，直接造成丢帧与漏判；
- 轮询线程：它同时是**取帧线程**。`imdecode + write` 实测原生 2560×1440
  14~41 ms/帧，一段 60 帧要 1~2.5 秒，期间相机帧在 `FrameBuffer` 里被覆盖。
  现场日志里 1.2~1.7 秒的「视频时间戳异常」有八成落在片段写盘窗口内。

所以判定线程只登记，轮询线程只收集帧与入队，真正的解码与编码由
`_ClipWriter` 单线程完成（2026-11 从轮询线程挪出）。

### 3.2 时间轴必须用「帧的采集时间（墙钟）」

片段是**给人看**的，时间轴要跟现场时间对齐：

- 缓冲里存 `frame.ts`（墙钟），不用 `media_ts`——示例回放那条时间轴与现场无关，
  而且回放不录片段；
- 事件的 `timestamp_start` / `timestamp_end` 来自**媒体时间**（判定计时用），
  与 `frame.ts` 不同源，**不能直接拿来做切片下标**。切片一律用被标记那几帧
  在缓冲里的实际位置（见 4.2）。

这条区别是本设计最容易踩的坑：示例回放 0.5× 时媒体时间只走了一半，而墙钟
走了一倍，两者相差 2 倍。

## 4. 判定细节

### 4.1 缓冲容量

```
容量帧数 = ceil((clip_pre_seconds + clip_margin_seconds + oiling_timeout_s) × fps) + 4
```

现场配置下是 `(3.0 + 1.5 + 5.0) × 15 ≈ 143` 帧，约 **9.5 秒**历史。前三项里
真正驱动下限的是 `margin + timeout`（事件起点比事件到达时刻早整整一个超时窗）。

### 4.1.1 缓冲存 JPEG，不存原始帧

原始 2560×1440 帧 11MB，9.5 秒要 **1.5GB** 内存，现场机器扛不住。所以每帧
在轮询线程里编码成 JPEG 再入缓冲：

| 编码 | 每帧 | 9.5 秒缓冲 | 编码耗时 |
| --- | --- | --- | --- |
| 原生 2560×1440 q=75 | ~2.2MB | **~75MB**（实测） | ~12ms |
| 1280×720 q=75 | ~0.37MB | ~45MB | ~2ms |

实测（示例视频、原生分辨率）：缓冲峰值 **74.6MB**，产出片段仍是
2560×1440。写片段时解码回 BGR 交给 `VideoWriter`。

编码在**轮询线程**里做（每帧约 5~12ms，实测真实画面约 4.6ms，可接受），
解码写盘在 `_ClipWriter` 线程里做；`clip_buffer_width` 可把缓冲降到
720p（复核看动作够用，编码也降到 ~1.5ms），`clip_buffer_max_mb` 是硬上限
——超过就丢最旧的帧并记一条 warning，宁可缓冲短一点也不 OOM。

`pre_seconds` 只覆盖「事件到事发」的固定延迟吗？不是——固定延迟由
`post_seconds` 与「从 `picked_at` 起算」共同解决。`pre_seconds` 是**保险**：
覆盖判定结算本身的抖动（攒采样、涂油段收尾）。

例：`oiling_timeout` 在第 10 秒判出，需要回看到取料那一刻。若把片段起点定成
`event.timestamp_start`（= `picked_at`），而 `picked_at` 发生在 10 秒前，
缓冲早就没那段了。**所以起点要从事件里取，不能只靠缓冲长度。**

### 4.2 三种起点来源，按优先级

```
1. 事件带 review 时间线里的 PICKED 时刻（_Cycle.timeline 里的 ("PICKED", ts)）
2. 事件 evidence 里的 picked_at
3. 都没有 → 缓冲里最早的一帧
```

这三者都是**媒体时间**，而缓冲是按墙钟排的。两者换算靠一个持续的偏移估计：

```
offset = frame.ts - pipeline_ts            （每帧更新，取最近 N 帧中位数）
clip_start_wall = event_start_media + offset
```

`pipeline_ts` 就是 `_poll_station` 里传给 `_process_frame` 的那个值
（实时相机回退成 `frame.ts`，示例回放是 `media_ts`）。实时相机上 offset 恒等于
`frame.ts - frame.ts = 0`（媒体时间回退到了墙钟），所以这个换算对现场是恒等的，
只有回放才会真有偏移——而回放不录片段。保留它只是为了**同一套代码在回放联调时
也能正确切分**，便于验证。

### 4.3 起点与终点的余量

事件里的起止是**判定口径**，不是人手看到的动作边界。实际切分时前后各放宽
`clip_margin_seconds`（默认 **1.5 秒**）——取料前手已经在盘上方伸过来，
判出后还要放下件、抬头、去取下一件，留出余量才能看清完整过程：

```
margin      = clip_margin_seconds       默认 1.5
start_wall  = event_start + offset - margin
end_wall    = max(event_end + offset, event_start + offset) + margin + post_seconds
```

`post_seconds` 在余量之后再叠加：它的作用是让人看到「接着去取下一件」
这个因果关系，而 `margin` 只是补齐这一件自身的动作边界。

**终点直接用事件口径的 `event_end`（判出 NG 的那一刻）。** 漏涂的
`timestamp_end` 正是「等满 `oiling_timeout_s` 才判出 NG」的时刻，这一整个
等待窗属于「完整过程」的一部分，**不裁**：

```
end_wall = max(event_end, event_start) + offset + margin + post_seconds
```

`clip_post_seconds` 默认 **2** 秒：判出 NG 之后工人往往立刻回头处理（放下
工具、重新拿杆），这一段能看清后续动作。超过 `end_wall` 的帧**不收进片段**
（`_collect_locked` 遇到就停），片段长度只由事件口径决定，不会因为收尾晚
半拍把后面无关的画面带进来。

NG 事件里 `timestamp_end`（=`ts`，判出那一刻）通常就是「这一件最后被看到」的时刻，
再接 `post_seconds` 让复核员看到「人接着去不停手地取了下一件」这个因果关系。
`superseded_by_pick` 的终点天然落在那次新取料的结算处，正好。

### 4.4 起止都不在缓冲里时

缓冲被长时间空转冲掉（相机断流后又恢复、事件在缓冲为空时到达）时：

- 能拿到起点帧就录，拿不到就从缓冲最早一帧开始（不伪造黑帧）；
- `evidence["clip_truncated"] = true`，复核页在结果里看到就知道「片段不全」。

### 4.5 结束条件（什么时候写出文件）

满足任一即写出：

1. 缓冲里出现了 `>= clip_end_wall` 的帧（正常路径）；
2. 相机离线 / 视频停播超过 `clip_finalize_timeout_s`（默认 3 秒）尚无新帧；
3. 服务 shutdown；
4. 缓冲被下一次登记挤掉（同一相机最多同时挂 `clip_max_pending` 段，默认 2）。

写出后立刻回填事件的 `clip_reference`，**不等到全部结束再补**：
`EventStore.update_clip(event_id, path)` 把内存里那条事件换成带路径的副本，
并追加一行 `clips-YYYY-MM-DD.jsonl` 映射记录（追加日志，不改旧行，
与 reviews 的做法一致）。

## 5. 存储布局

```text
<数据目录>/clips/
  2026-11-27/
    TASK-000123_oiling_missing_20261127_091512.mp4
    TASK-000123_oiling_missing_20261127_091512.json     # 片段元数据
  clips-2026-11-27.jsonl                                 # event_id → 路径
```

片段元数据与训练录制同构，便于同一套工具读：

```json
{
  "type": "event_clip",
  "status": "finished",
  "event_id": "...",
  "event_type": "OILING_MISSING",
  "reason": "oiling_missing_timeout",
  "task_id": "TASK-000123",
  "station_id": "ST01",
  "camera_id": "cam_6ca47a",
  "path": ".../TASK-000123_oiling_missing_20261127_091512.mp4",
  "fps": 15,
  "width": 2560,
  "height": 1440,
  "frame_count": 187,
  "truncated": false,
  "started_at_epoch": 1795742112.4,
  "ended_at_epoch": 1795742124.9
}
```

命名用 `task_id + 事件类型 + 时刻`，复核员在文件管理器里也能直接认出来。

## 6. 配置

`config/oilcheck.json` 的 `recording` 段（已有 `event_clips_enabled` 预留开关）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `event_clips_enabled` | **false** | 总开关。默认关：写盘与训练录制抢同一块盘，现场确认硬盘余量后再开 |
| `clip_dir` | `clips` | 片段目录，相对数据目录解析 |
| `clip_pre_seconds` | 3.0 | 环形缓冲长度（秒）。只作保险，见 4.2 |
| `clip_margin_seconds` | 1.5 | **事件自带的起止之外，前后各再延长多久**。取料前手已经在盘上方伸过来，判出后还要有现场反应 |
| `clip_post_seconds` | **2** | 事件后再额外录多久。判出 NG 后留 2 秒，看清工人随后的处理动作 |
| `clip_buffer_width` | 0 | 缓冲缩放宽，0 = 原生分辨率。720p 可把缓冲从 75MB 降到 45MB |
| `clip_jpeg_quality` | 75 | 缓冲 JPEG 质量 |
| `clip_buffer_max_mb` | 512 | 环形缓冲内存上限，超过丢最旧的帧并记 warning |
| `clip_fps` | 0 | 0 = 跟 `recording.fps`。片段比训练录制更需要「动作完整」，不建议低于 10 |
| `clip_codec` | 空 | 空 = 跟 `recording.codec` |
| `clip_max_pending` | 2 | 每相机同时挂起的片段上限 |
| `clip_retain_days` | 30 | 启动时清理超过该天数的片段（0 = 不清） |

四个「新增键」都要同时改：dataclass 字段、`to_dict`、`from_dict`、
`CONFIG_COMMENTS`，并按注释表重新渲染 `config/oilcheck.json`。
`event_clips_enabled` 已经存在，**注意不要**把它挪进 `_PIPELINE_REMOVED_2_4`。

## 7. 关键取舍

### 7.1 为什么不用「持续录制 + 事后裁剪」

持续录制已经在做（训练录制）。理论上可以事后按时间戳从训练录像里裁，但：

- 训练录制是**可选的**，现场多数时间没开；
- 分段边界（默认 5 分钟）会切开目标片段，裁剪要跨文件拼接；
- 裁剪要解码再编码，比「环形缓冲直接写」贵得多，且要等分段 `finalize`
  （最多 5 分钟）才拿得到。

环形缓冲只持有 `pre_seconds × fps` 帧（3 秒 15fps 的 2560×1440 ≈ 66MB/相机），
内存可控，且事件一到立刻就能开始写。

### 7.2 为什么不复用 `TrainingRecorder`

`TrainingRecorder` 是**常开**的连续分段录制，没有「从缓冲中间起算」和
「按事件截断」的能力。强行复用会让它的分段语义变复杂（一段里混着多件料）。
片段服务独立一个类，两者共用 `recording.codec/fps` 的默认值即可。

### 7.3 编码资源

片段写盘与训练录制同时打开时，一台工控机的 CPU 编码可能吃紧。缓解：

- 片段只在 NG 时触发（现场频次低）；
- `clip_max_pending` 限制并发；
- 队列满时**丢帧而不是阻塞**（与训练录制同一策略），并在元数据里记
  `dropped_frames`。

## 8. 失效模式与对策

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| 复核页「播放片段」仍提示「无视频片段」 | 开关没开 / 回放模式 / 事件是确认类 | 复核页消息要区分这三种，见 §9 |
| 片段比自己预期短 | 缓冲在事件前被冲掉 | 元数据 `truncated=true`；调大 `clip_pre_seconds` |
| 片段动作速度不对 | 用错了时间轴（4.2 的坑） | 片段时长应≈`post_seconds + (事件时刻 − 起点)`；用测试卡住 |
| 视频打不开 | 服务被 kill -9，writer 没 release | 与训练录制同一已知限制；正常退出走 `aboutToQuit` |
| 磁盘涨得快 | 只增不删 | `clip_retain_days` 启动时清 |

## 10. 测试

新增 `tests/test_event_clips.py`：

1. **环形缓冲**：push 超过容量只保留最新 `pre_seconds` 帧。
2. **正常路径**：伪造 30 帧 + 一个 `NEEDS_REVIEW` 事件 → 产出片段，
   `frame_count` 覆盖「起点 → 事件 + post」。
3. **起点回看**：事件 `picked_at` 在缓冲范围内时，片段起点对齐它；
   超出缓冲时 `truncated=True` 且不抛异常。
4. **超时收尾**：事件后不再有帧，超过 `clip_finalize_timeout_s` 也要写出文件。
5. **开关**：`event_clips_enabled=false` 时一个文件都不写。
6. **回填**：写出后 `EventStore` 里对应事件的 `clip_reference` 已更新，
   且 `clips-*.jsonl` 有一行映射。
7. **时间轴**：片段 `frame_count / fps ≈ 片段真实时长`（防 4.2 那个坑）。
8. **余量**：默认前后各延长 1.5 秒，片段覆盖完整动作。
9. **完整过程**：取料前 1.5s → 判出 NG → 后 1.5s，含中间整个超时等待窗。
10. **缓冲容量**：盖住 `margin + timeout`；内存上限生效时丢最旧的帧。

服务层集成测试（`tests/test_service_config_reload.py` 同目录新建）：
用假的相机会话推 N 帧，注入一条 NG 事件，断言片段文件存在且可被
`cv2.VideoCapture` 打开、帧数 > 0。

## 11. 实施顺序

1. `app/oilcheck/clips.py`：`_ClipBuffer` + `EventClipService`（纯逻辑，可单测）；
2. `config.py` 加 6 个键 + 注释 + 重渲染模板；
3. `service.py` 接线：`_poll_station` 里 push、`_on_event` 里登记、shutdown 收尾；
4. `events.py` 加 `update_clip`；
5. `review_page` 文案 + 设置页开关；
6. 文档 `docs/07 §9` 从「当前版本未实现」改成指向本篇；
7. 单测 + 服务层集成测试。

第 1、2 步不依赖任何现场条件，可以先合；3~5 步等现场确认硬盘余量、把
`event_clips_enabled` 打开后再启用。
