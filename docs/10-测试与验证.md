1. `uv run python main.py`；
2. 监控页选择工位；
3. “画面源”下拉选择任一示例（`data/sample_video` 下的录像，显示成
   `日期_时间`，例如 `20261027_105708`）；

   - 顶部状态条显示 `检测：xx.x ms · imgsz 1024 · N目标（hand x / brush x /

   - 画面上的框覆盖模型输出的全部类别；
   - 状态条信息行显示 `示例回放 名称 · 进度%`；
   - 示例回放**不写入训练录制**；
4. 把 `detector.raw_mode` 设为 `false` 后重启，即恢复取料/涂油判定，
   观察任务阶段变化：`WAITING_PICK → PICKED → OILED`，

   出现「人工二次涂油未完成」说明该件被下一件打断，属于预期外的漏涂。

### 2.1 二级判定（规则 + 随机森林复核）的稳定性

线上除了 `pipeline.py` 的规则，还有一层「二级判定」：规则拿不准的那一段
交给 `config/judge_pick.json` / `config/judge_oiling.json`（ExtraTrees，
`tools/train_judge.py` 生成）补一票。只用**原始检测框特征**（落手面积、
杆/手位移、盘内杆数变化……），不读规则已经算好的结论。

两层怎么融合（取料）：规则多数投「是」但模型概率 < `_RULE_TRUE_VETO_P`
(0.40) ⇒ 改判「否」；规则投「否」但见过握持 ⇒ 模型说了算；一帧握持都没
见过 ⇒ 空手离开，两层都判否。**否决必须一路传到事件**：`_settle_pick`
拿到 `decision=False` 就要 return，否则记了概率却没生效（见 2.1.2 第 1 条）。

用线上完全相同的 `StationPipeline`（含二级判定）跑这 9 段视频，逐视频
取料/涂油次数与上表**全部一致**（23 取 / 26 涂）：

| 帧率 | 逐视频一致 | 合计 | 重复 2 次是否变化 |
| --- | --- | --- | --- |
| 15（原始） | 9/9 | 23 / 26 | 无 |
| 12 | 9/9 | 23 / 26 | 无 |
| 10 | 9/9 | 23 / 26 | 无 |
| 7.5 | 9/9 | 23 / 26 | 无 |

判定是确定性的（没有随机数、不依赖线程时序），同一份录像重复跑结果完全
一样；上表的「重复 2 次」只是把这件事实测出来。帧率降到 7.5 仍一致，说明
帧率自适应的放大没有把门限撑到失去区分度。

> 注：上表是加进 122925 之后那一批改动之前的数字。当前 11 段视频的验收
> 口径见 2.1.1 / 2.1.3，现场真值见下面的视频 11 说明。

#### 2.1.1 帧率往上走：15fps 录像插到 20fps

现场相机主码流 25fps、判定侧 `pipeline.max_fps=20`，而示例录像都是 15fps。
15fps 上判得对不等于 20fps 节拍下也判得对——原先判定里有大量「按帧计数」
的门限（采样窗口、连续帧数、静置对照窗口），帧率一变，同一段动作的帧数就
变，结论跟着变。两件事都做了：

1. **把判定改成与帧率无关**（见 2.1.3），这是根；
2. 把 11 段录像**运动补偿插帧**到 20fps（不是重复帧：同一画面算两次会让
   「连续帧数」门限提前满足），用线上完全相同的判定跑一遍做验收。

```bash
uv run python tools/interpolate_videos.py          # data/sample_video → data/sample_video_20fps
uv run python tools/eval_fps_baseline.py --dir data/sample_video_20fps
uv run python tools/eval_fps_baseline.py --dir data/sample_video   # 同口径 15fps 对照组
```

`eval_fps_baseline.py` 直接按文件帧率解码、挂 `config/judge_*.json` 二级
判定，基准取 `data/operations_preview/*.json` 的独立清点（按文件名配对）。

插帧用 ffmpeg `minterpolate`（mci + aobmc + bidir），2560×1440 上约
30s/视频秒、单进程满一核，全部 11 段要二十分钟上下。产物在
`data/sample_video_20fps/`（未跟踪），文件名与原始一致，时长不变。

**结果：20fps 与 15fps 逐视频一致 10/11**。其余 10 段两档次数完全相同；
122925 在 15fps 下是 17 取 / 16 涂 / 1 NG（与现场一致），20fps 下是
15 取 / 16 涂 / 0 NG——**这一段还没对齐**，原因已定位到插帧后同一根杆
被检出两个交叠框（40.15s 的 (1608,520) 135×29 与 (1630,561) 132×43，
置信度 0.61/0.53，前后帧都只有一个 0.84+ 的框），丝杆出盘记录因此分叉。
两档合计 15fps 是 44 取 / 46 涂、20fps 是 42 取 / 46 涂。

要在监控页里真正跑满 20fps，`demo.fps_limit` 必须同样 ≥20
（`config/oilcheck.json` 与 `DemoConfig` 默认值都已改成 20；现场配置若仍是
15，回放会按 15 投放、等于白插帧）；15fps 原始录像仍按自身帧率投放，
不受影响。

**严格帧率对照**（排除插帧本身的画面变化）：同一段 20fps 内容每 4 帧取 3
帧，得到 15fps 网格、时长不变，两档跑同一份判定，次数应完全一样。这是
2.1.3 那组改动的验收口径——只换时间网格，画面与检测结果都不变。

**改判定的回归口径**：改完 `pipeline.py` 或重新训练权重后，按下面几条验：

```bash
uv run python tools/eval_against_baseline.py     # 线上判定 vs 清点：逐条列出漏判/多判
uv run python tools/train_judge.py               # 重新采集 + 训练，看「按视频分折」是否仍 9/9
uv run python tools/eval_events.py               # 事件级：各算法留一视频的次数对齐情况
uv run python tools/eval_raw_features.py         # 只用原始检测框特征的留一视频对比
```

`eval_against_baseline.py` 是逐条对账：除了次数，还把每一处**漏判/多判的
时刻**打出来，并区分取料来源（手部判据 / 丝杆判据）。配对按区间中点距离
（默认 2s）——判定结算天然晚于动作区间，按重叠比会把真动作标成「一多一漏」。

`train_judge.py` 的训练集自检（acc=1.000）没有参考价值——样本少、树模型
必然拟合。**只看「按视频分折」那几行**：那是留出一整段录像的预测，换一段
录像还能不能判对才有意义。

#### 2.1.2 视频 11（122925）的判定修复

那一轮排查改了六处，每一处都有明确的现场症状：

1. **规则投「是」时模型否决没落地**。`_judge_pick` 早就按
   `_RULE_TRUE_VETO_P`（0.40）把 `decision` 改成 False，但 `_settle_pick`
   只检查 `not verdict`，否决等于没生效。症状：122925 第 1 秒工人把夹具
   摆到工位上，手在盘区停 3.1s，规则投真、模型 p=0.14 明明判否，仍报取料
   并连带一次漏涂 NG。修好后该件不再上报。
2. **正在刷的那根杆整帧漏检时不算接触**。现场每次刷 1.0~1.4s，中间拳头
   压住杆、那根整帧检不出，但**盘里别的杆还在**，所以走不到「一根杆都
   检不到」的整帧遮挡桥接，接触被切成 0.2~0.3s 碎段、累计停在 0.93s。
   `_oiling_rod_occluded_contact` 在「锚点附近确实没有杆框 + 刷头仍贴着
   锚点」时按锚点补时间，总补时长受 `brush_hold_max_gap_s` 限制（纯时间，
   不乘帧率倍率，见 2.1.3）。修好后涂油 8 → 16，与现场清点一致。
3. **丝杆出盘记录被盘内静置杆长期占坑**。盘里那排杆从视频开头就在、
   一直不动，每条都留着记录（实测同时 14 条），后来真被取走的那根抢不到
   新记录，「在盘里放稳 → 出盘」这条流程永远走不到。改成静止记录活过
   `_SCREW_EXIT_IDLE_RELEASE_S`（2s）就释放，动过的记录（`active`）长期留。
4. **出盘框不像杆也判了取料**。长宽比门限只在**建记录**时查（`_ROD_MIN_ASPECT`
   = 2.0）。曾试过在**出盘确认**时再查一遍，用来挡 102.8s 那个 123×98、
   长宽比 1.26 的方块误检——但那样会把 40.13s 那次真取料一起挡掉（真取料
   离盘时框被拉成 132×43、长宽比 3.0 上下浮动），122925 的取料从 17 掉到
   16。**该门限已删除**，方块误检改由「盘心必须出盘 + 连续 2 帧在盘外」
   这组条件消化。
5. **出盘记录的起点被锁死在「第一次动」**。`moving_since_ts` 只在第一次
   判为非静止时置一次，盘里的杆整段有几处检测框抖动，事件区间就被拖成
   「0.07–4.73s」这种（真实 3.87–4.53s）。改成跟着最近一次开始移动走。
6. **涂油挂不上取料周期**。原先 `_oiling_target_cycle` 在「取料那只手
   没握着这根杆」时就按「手还在画面里 ⇒ 这根杆不归这一件」直接放弃，
   连位置对得上也不看。现场工人取完料把杆换到另只手上继续刷时，手部
   那一路必然判不出来，位置这一路还可靠（122925 13.33s 那次刷的就是
   13.00s 取出的那根）。改成**先按位置认、位置对不上才看手**；修好后
   三处误报漏涂 NG 全部消失。
7. **带料进盘后取走盘里另一根，被整件跳过**。87.07s 那次工人先把一根
   杆带进盘、在盘里整理，随后把**盘里的另一根**带出去（离盘手里那根
   是 1782,579，不是带进来的 84.33s 那根）。原先把「带料进盘」一刀切
   跳过，这次取料丢掉，后面那件还被顶成漏涂 NG。新增
   `_same_rod_as_entry`：带出去的仍是带进来那根才跳过。

同一次排查还修了事件区间错位：手部轨迹 ID 会被跟踪器复用，上一次进盘
留在队列里的分段会被下一次取料取走，事件起点被拖到几十秒前（96.5s 那次
取到 89.2s 的区间、99.5s 又取到 96.5s 的）。现在按 owner 匹配时也要求
区间终点不早于本次结算 `screw_exit_pick_dedup_s`。

**视频 11 的现场真值以人工清点为准：17 取 / 16 涂 / 1 次 NG**，NG 落在
86–87s 那次取料上（现场无紧接刷油）。`data/operations_preview/
cam_6ca47a_20261127_122925.json` 的 16 取 / 10 涂是脚本自己的口径，
**对这一段是偏低的**（脚本要求连续接触整段达标，这一段每次刷 1.0~1.4s
且反复被拳头中断）。线上 15fps 回放给出的正是 17 / 16 / 1，与现场一致；
`eval_fps_baseline.py` 对这一段显示 ✗ 是基准本身的问题，不是判定错。

回归：其余 10 段视频的取料/涂油次数**一个都没变**（含两段 0/0 负例）；
`uv run pytest` 379 项全过，其中 `tests/test_oiling_occlusion.py` 是补帧
行为的专项（含「补帧有上限」「杆在锚点可见时不补」两条反例）。

#### 2.1.3 判定与帧率解耦

原先判定里有三处「按帧计数」，同一段动作换个帧率就给出不同结论（实测把
122925 插到 20fps 后取料 17 → 13）。现在全部改成按**时间**：

| 原来 | 现在 |
| --- | --- |
| 取料采样每 `pick_sample_every_frames` 帧一个点 | 每 `k / 15` 秒一个点（`_PICK_SAMPLE_CALIBRATION_FPS`），点数按时间攒 |
| 静置杆对照「`_SCREW_STATIC_BACK` 帧前」 | 「`_SCREW_STATIC_LOOKBACK_S` 秒前」= 8/15 秒，丝杆历史按时长裁剪 |
| 落手面积达标累计 `_CARRY_INHAND_FRAMES` 帧 | 累计 `_CARRY_INHAND_S` 秒 |
| 丝杆出盘连续 `_SCREW_EXIT_MIN_FRAMES` 帧 | 已有 `_SCREW_EXIT_MIN_OUTSIDE_S`（纯时间），帧数这条不再起作用 |

反向的一类也修了：`brush_hold_max_gap_s`、`screw_anchor_hold_s`、
`holding_lost_timeout_s`、`_CARRY_OUT_OF_TRAY_MAX_S` 这些**本来就是秒**
的门限原先还乘了 `frame_scale`（15fps 下 1.33、20fps 下 1.0），等于帧率
越高越严格。现在它们不缩放，只加「至少覆盖一个实际帧间隔」的下限
（`_at_least_frame`）——2fps 时门限比一帧还短会让任何两帧都被当成「超出
补回上限」。

**验收**：同一段 20fps 内容每 4 帧取 3 帧降到 15fps 网格（画面、检测、
时长都不变，只变帧率），10/11 段两档次数完全一致。122925 这一段的差异
不来自帧率门限，而来自插帧把同一根杆插出了两个交叠检测框（见 2.1.1），
属于检测层面的噪声，不是判定随帧率漂移。

### 2.2 事件的起止时刻

事件的 `timestamp_start` 是**动作本身**的起点，不是「证据攒够」的那一帧：

- 取料：手进盘 → 带杆出盘；
- 涂油：刷头第一次贴上 → 这次接触结束。

取料与涂油并行判定，工人常常取完料过几秒才开刷（105708：13.0s 取料、
18.0s 开刷）。涂油事件的起点取**这次接触**的开始，不退回取料时刻——否则
复核页会把区间显示成「从取料横跨到刷完」，核对时间点对不上。

与脚本清点的起始时刻对照：

| 视频 | 涂油事件起点 | 脚本清点 |
| --- | --- | --- |
| 105708 | 18.0 / 25.6 / 31.6 / 37.67 | 18.0 / 25.6 / 31.6 / 37.667 |
| 140911 | 0.53 / 8.0 / 16.13 / 23.2 | 0.533 / 8.0 / 16.067 / 23.2 |
| 091519 | 0.07 / 6.07 / 15.4 | 0.067 / 6.067 / 15.4 |
| 094439 | 0.73 / 8.6 / 15.13 / 23.13 | 0.733 / 8.6 / 15.067 / 22.533 |
| 092817 | 1.33 / 6.47 / 13.0 | 1.333 / 6.467 / 13.0 |
| 153539 | 5.87 / 10.13 / 13.0 / 16.73 | 5.867 / 10.067 / 12.933 / 16.733 |
| 170216 | 0.07 / 6.07 / 11.93 / 15.6 | 0.067 / 6.067 / 11.8 / 15.6 |

两处偏差略大，都是**帧率量化**而不是判错：

- 094439 第 4 件晚 0.6s：这一段开始得晚，脚本从「刷头首次接触」算，
  线上的涂油段要求同一根杆连续确认，起点落在确认后的那一帧；
- 170216 第 2 件晚 0.13s：脚本清点与线上回放落到相邻两帧。

次数与前后顺序都对得上；偏差不超过 0.6s，且总是**晚**（起点不会比脚本更早，
不会把上一件的尾巴算进这一件）。


与监控页的差异来自两处，都是预期内的：

- **录像开头那一件**：091519 从 0.07s 就在刷、094439 从 0.73s 就在刷、
  170216 从 0.07s 就在刷，取料发生在录制开始之前；监控页按作业周期判，
  只能看到取料之后的涂油；
- **092817 第 2 件**（5.93s）：监控页把它判成「盘内停留 2.80s 的取料」，
  实际是工人把手伸进盘里按住夹具、顺手把杆停在盘区下沿刷，
  这里判为一次取料 + 一次涂油，不复用作业周期的结论。

170216 还有两处是「目视核对过、确实该这么判」的：

- 13.7~14.6s 手把杆放到盘边、空手离开，**不是**取料（杆没被带走）；
- 19.3s 之后刷手还在动，但手里已经没有杆（模型也检不到丝杆），
  后面的接触不累计。

逐条回看（打开窗口播放，并标出每一次动作）：

```bash
uv run python tools/play_operations.py                 # 依次播放全部已出结果的视频
uv run python tools/play_operations.py --video 6       # 只看第 6 段（1 基）
uv run python tools/play_operations.py --speed 0.5     # 半速
uv run python tools/play_operations.py --video 6 --snapshot 10.4   # 只存一张核对图
```

画面左侧实时显示当前正在发生的动作（取料闪黄框、涂油显示接触时长），
右侧是这段录像的**全部**动作时间线：`✓` 已发生、`▶` 正在发生、`·` 还没到。
按键：空格暂停、`[` / `]` 跳到上/下一次动作、`r` 重播、`Esc` 退出。
读的就是 `detect_operations.py` 的 JSON，所以判定改了重跑检测即可，
播放器不用改。`--snapshot` 可以在没有图形界面的机器上导出核对图。

## 3. 离线回放验证

推荐用训练录制页采集现场视频，再离线回放：

```python
import cv2
from app.oilcheck.config import OilCheckConfig
from app.oilcheck.detector import create_detector
from app.oilcheck.pipeline import StationPipeline
from app.oilcheck.types import EventRecord

station = OilCheckConfig.from_dict(...).stations[0]
detector = create_detector(station)          # 真实模型接入后为 yolo
events: list[EventRecord] = []
pipeline = StationPipeline(
    station=station,
    pipeline_cfg=cfg.pipeline,
    on_event=events.append,
    cycle_id="REPLAY",
    detector_name=detector.name,
)

cap = cv2.VideoCapture("recording.mp4")
fps = cap.get(cv2.CAP_PROP_FPS) or 15
ts = 0.0
while True:
    ok, frame = cap.read()
    if not ok:
        break
    ts += 1.0 / fps
    pipeline.process(detections=detector.detect(frame, ts))

for e in events:
    print(e.to_dict())
```

要点：

- 时间戳用视频帧序号/帧率，不要用 `time.time()`，否则阈值行为不对；
- 人工标注真实事件区间，与回放输出按时间匹配；
- 分别统计取料和人工二次涂油，不要合并；
- 正常生产只出现 `PICK` 与 `MANUAL_OILING`；出现 `OILING_MISSING` 说明该件
  取走后没刷够就被下一件打断，需要现场核对；
- 先调阈值，再上现场实时试运行。

## 4. 现场数据采集建议

按方案 P0：

- 覆盖正常取料、提前取料、4 根交错、手部遮挡、调整位置、短暂停留、二次涂油、
  普通拿取、空位等场景；
- 每个班次/光照条件至少若干分钟连续视频；
- 记录相机位置、镜头、分辨率、节拍；
- 人工标注事件起止时间、位置、结果、是否遮挡；
- 标注规范统一后再统计，避免“取料”定义不一致。

## 5. 验收指标

分别对取料与二次涂油统计：

| 指标 | 计算 |
| --- | --- |
| 召回率 | 系统确认的真事件 / 人工标注真事件 |
| 准确率 | 系统确认事件中真事件的比例 |
| 待确认比例 | 进入 `NEEDS_REVIEW` 的事件 / 人工标注事件（或系统事件） |
| 事件延迟 | 动作实际结束到 UI 显示确认结果的时间 |
| 误报原因分布 | 按 `evidence.reason` 统计 |

注意：

- 不能用目标检测 mAP 代替流程指标；
- 待确认不是“错”，但要单独报告，因为它意味着人工介入成本；
- 目标值需业务方根据漏检风险、误报处置成本、现场节拍共同确定。
