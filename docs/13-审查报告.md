## 1. 判定正确性

### R1 严重：`pick_confirm_s` 没有衡量「盘内停留」，盘边划过会被判成取料

文档 [05](05-状态机与事件规则.md) §4.2 第 3 条写的是「盘内停留 ≥ `pick_confirm_s`」，
但实现里**没有任何地方记录盘内时长**：

- `app/oilcheck/pipeline.py:862` 创建 `_HandVisit` 时把 `entered_tray_ts` 设为
  **首次见到这只手**的时刻，不是确认进盘的时刻；
- `app/oilcheck/pipeline.py:1017` 用 `dwell = ts - visit.entered_tray_ts` 作为
  「盘内停留」。

手在盘区外被持续跟踪得越久，`dwell` 越大，「从盘边划过不判取料」这道守卫
就被撑得越松。

**复现**（15fps、`pick_confirm_s=0.3`；手先在盘外被连续跟踪 3 秒，只把盘区
蹭过 1~2 帧，随后在盘外拿起一根杆走开）：

| 盘内实际停留 | 结果 | 事件记录 `dwell_in_tray_s` |
| --- | --- | --- |
| 0.07 s（1 帧） | 误判 `PICK/CONFIRMED` | 3.80 |
| 0.13 s（2 帧） | 误判 `PICK/CONFIRMED` | 3.93 |

对照：把 `pick_confirm_s` 调到 5 s 后同一段动作不再判取料，反证该阈值比的是
「首次见到手 → 结算」的时长。正常取料路径（盘外只走几帧）不受影响。

**修法**：按帧累计 `inside_raw` 为真的时长（或至少记录进盘区间的真实起止），
`dwell` 用它。只在 `entered_confirmed` 置真处补记时刻**不够**——确认本身要等
采样点撞上盘内帧，仍滞后于真实进盘。

### R2 严重：系统时钟回拨会让判定永久停摆

实时相机帧的时间戳是墙钟（`hik/decode.py:33` 的 `time.time()`）。
`app/oilcheck/service.py:736`（`if frame.ts <= runtime.last_frame_ts: return`）
会静默丢弃「时间倒退」的帧，而 `last_frame_ts` 只增不减；`app/oilcheck/pipeline.py:459`
在管线内部还有第二道同样的守卫。

**复现**：正常跑 10 秒后把时钟回拨 60 秒，继续喂 150 帧 —— 实际处理 0 帧，
`_frame_gap_events` 记录 150 次「视频时间戳倒退」。系统要等墙钟追上
`last_frame_ts` 才恢复。

比停摆本身更麻烦的是**没有任何痕迹**：相机状态仍是 `previewing`，
`station_snapshot` 的 `time.time() - last_ts < 5.0` 因差值为负恒判在线，
界面显示「在线、有画面」，日志里也没有一条 warning——这处丢帧发生在进入
管线之前，绕过了 `app/oilcheck/pipeline.py:459` 那处专门写了警告的处理。

工控机 NTP 校时、手工改时间、断电重启后对时都是常规操作。同一根因还让
录制分段切分（`app/oilcheck/recorder.py:241` 用 `ts - segment.started_at`）
在回拨期间不切段。

**修法方向**：帧间隔用 `time.monotonic()` 或媒体时间承载，墙钟只用于记录展示；
或在 service 层检测到倒退时记 warning 并重置 `last_frame_ts`
（参照 `_reset_on_video_rewind` 的做法）。

### R3 中：`_f` 把 NaN 静默夹成 0.0，一组阈值同时失效

`app/oilcheck/config.py:195` 的 `_f` 实现为 `max(lo, min(hi, float(v)))`。
`min(hi, nan)` 在 Python 中返回 `hi`，因此 NaN 不会报错，而是落到某个边界值。

**复现**：把 `pick_confirm_s`、`brush_hold_s`、`brush_contact_distance`、
`oiling_timeout_s` 分别写成 NaN，加载后**全部变成 0.0**：盘内停留门槛归零、
涂油门槛归零、接触距离归零、漏涂超时被关闭。系统照常运行，只是判定全部
失去约束。

**修法**：`_f` 显式拒绝非有限值（`math.isfinite`），非法时回退默认值并记日志。

## 2. 配置系统

### R4 严重：两个取料判定核心参数从不解析

`PipelineConfig.from_dict`（`app/oilcheck/config.py:413` 起）的 `cls(...)`
构造里没有 `pick_sample_every_frames` / `pick_history_samples`：字段已声明
（294–295 行）、`to_dict` 会导出（586–587 行），但**读取时永远取默认值 2 / 3**。

**复现**：`PipelineConfig.from_dict({"pick_sample_every_frames": 7, "pick_history_samples": 9})`
得到 2 / 3。现场把文件改成 7 / 9 不生效；之后在设置页点一次保存，还会把它们
写回 2 / 3。

`tests/test_config.py:781` 的注释正好点名了这两个参数是「写了不生效」的典型，
但该测试只断言「文件里的值 == cfg 里的值」——两边都是默认值，测不出问题。

**修法**：补 `_i("pick_sample_every_frames", ...)`、`_i("pick_history_samples", ...)`；
测试改成先写入非默认值再断言生效值。

### R5 严重：`bool("false") == True`

`app/oilcheck/config.py:852`、`853`（`PlcConfig`）与 `962`（`StationConfig`）
直接用 `bool(data.get(...))`，而同一文件里其他字段的 `_b()` 已经正确处理了
字符串白名单。

**复现**：`PlcConfig.from_dict({"enabled": "false", "dry_run": "false"})` 得到
`enabled=True, dry_run=True`；`StationConfig` 的 `enabled="false"` 同样为真。
手写字符串是现场编辑 JSON 的常见错误，后果是 **PLC 线程意外启用并真的写寄存器**，
或启用本应停用的工位。

**修法**：这两处改用与 `_b` 相同的解析（字符串走 `{1,true,yes,on}` 白名单）。

### R6 严重：`cameras.json` 语法错误会被写回成空列表

`app/config_service.py:165` 在解析失败时返回空列表；而设备页的增、删、改
**每次操作都直接写盘**（`ui/pages/device_page.py:142`、`154`、`162`）。

**复现**：`cameras.json` 写成 `[{"id":"cam1",}]` → `load_cameras()` 返回 `[]`
→ 调一次 `save_cameras([])` → 文件内容变成 `[]`。两台相机的 IP、账号、密码
全部丢失。

### R7 高：语法合法但字段类型非法会让检测线程整个退出

`app/oilcheck/service.py:706` 的 `_reload_if_file_changed` 只保护了 JSON 语法
（`load_json_with_comments`），而 `load()` 内部的 `OilCheckConfig.from_dict`
抛出的异常不在保护范围内，会一路冒到 `_run`，使检测线程退出；此时
`_config_mtime` 已在 688 行更新，之后不会再重试。

**复现**：`{"pipeline": [1,2]}` → `TypeError`；`{"operation_max_active": "abc"}`
→ `ValueError`。

### R8 高：UTF-8 BOM 导致静默降级为零工位

`app/oilcheck/config.py:1954` 用 `encoding="utf-8"` 读文件；带 BOM 的文件
（Windows 记事本另存即产生）抛 `JSONDecodeError`，而
`app/oilcheck/config.py:1575` 随即 **返回全默认配置**。

**复现**：带 BOM 的 `oilcheck.json` → 日志一条 error → `stations = []`，
界面上没有任何提示。此后用户若在设置页保存一次，整份现场配置被默认值覆盖。

**修法**：改为 `encoding="utf-8-sig"`；解析失败时不要静默降级到默认配置。

### R9 中：`1e400` 让配置加载崩溃

`app/oilcheck/config.py:432` 的 `_i` 只捕获 `TypeError` / `ValueError`，
而 `int(inf)` 抛的是 `OverflowError`。Python 的 `json` 默认把 `1e400` 解析成
`inf`，因此配置文件里一个越界数值就能让 `load()` 抛异常，影响所有整型参数
（`max_fps`、`hand_track_min_hits` 等）。

### R10 高：旧配置迁移会丢掉只写了 `pick_roi` 的工位

`app/oilcheck/config.py:925` 明确支持 `tray_roi` 与 `pick_roi` 互为别名，
但 2.x 迁移分支会先删掉 `pick_roi`，之后该工位因缺少 `tray_roi` 被丢弃。

**复现**：只写 `pick_roi` 的 2.0 工位配置 → 迁移后 `stations = []`。原文件会
备份为 `oilcheck.json.bak`（可手工恢复），但程序本身不会提示。

## 3. 相机接入与重连

### R11 严重：`PlayM4_GetJPEG/GetBMP` 的 ctypes 签名漏了 2 个参数，截图会写穿堆

`hik/sdk_context.py:428-435` 把这两个函数声明为
`[playm4_port_type, c_char_p]` 两参数，调用点 `hik/session_actor.py:741` 传的
是**文件名**缓冲 `ctypes.create_string_buffer(path_bytes)`。

对 `lib/linux/libPlayCtrl.so` 反汇编核对实际 ABI：

```
PlayM4_GetBMP / PlayM4_GetJPEG 序言依次保存 edi / rsi / edx / rcx  ← 4 个参数
  ...
  lea    -0x38(%rbp),%rcx      ; arg3 的地址
  mov    -0x40(%rbp),%rdx      ; arg2（缓冲指针）
  call   MP_GetPictureData(handle, 0x18, arg2, &arg3, 0, 0)
  mov    %edx,(%rax)           ; 把图像长度写回 arg4 指向的地址
```

即签名是 `(int nPort, unsigned char *pBuf, unsigned int nSize, unsigned int *pSize)`
——`nSize` 是调用方给出的缓冲**容量**，`*pSize` 回写产生的图像长度。项目只声明
两个参数时，`edx/rcx` 是 libffi 的寄存器残值。

**实际失败链（已按反汇编逐条核对，与「整幅图像灌进路径缓冲」不同）**：

1. `arg3`（容量）取到残值，Chroma 层在 `CVideoDisplay::GetPictureData`
   （BMP 需 `w*h*4+54`、JPEG 需 `w*h*3/2`）先做容量校验，不足则直接返回
   `0x80000015`——**`pBuf` 不会被写**，所以不存在「整幅图像覆盖 path_buf」的堆溢出；
2. 随后 `0x2115de: cmpq $0x0,-0x48(%rbp)` / `je`，只有 `arg4` 非 NULL 时才执行
   `0x2115ec: mov %edx,(%rax)`，把长度写到 `arg4` 指向的地址。`arg4` 同样是残值
   ——**这就是野指针写**。

在 CPython 3.12 的 libffi 上 `rcx` 残值实测非 0，因此该写必然执行。调用发生在
actor 工作线程（`_do_snapshot`），一旦段错误**整个进程退出**，与现场「点截图后
程序消失」一致。若残值恰好落在可写内存，则不崩、只静默损坏内存并返回失败，
`_do_snapshot` 会回退到 `FrameBuffer` + `cv2.imwrite` 的正常路径。

**另有一层独立缺陷**：这套 API 从不写文件（只把图像写进内存缓冲），所以即使把
签名改对，`hik/session_actor.py:742` 拿到 `True` 时仍会 `return output_path` 而不校验
文件是否存在，UI 报「截图成功」而磁盘上没有文件。

**修法**：按 4 参数声明，调用方先取长度再自行分配缓冲，拿到内存数据后用
`cv2.imwrite` 落盘；或直接删掉 SDK 截图分支，只用 `FrameBuffer` 的 BGR 路径
（该路径本身是对的），并在返回前校验文件确实存在。

### R12 高：连接阶段抛异常会让会话永久卡在 CONNECTING

`hik/session_actor.py:252` 先迁移到 `CONNECTING`，随后 253 行 `initialize()`、
254 行 `_ensure_lease()` 才可能抛错；而 `_handle_command`（`hik/session_actor.py:200`）
只把异常塞进 reply，**不设置会话状态**。

之后：
1. `ReconnectPolicy.should_reconnect`（`app/reconnect_policy.py:94`）对
   非 PREVIEWING / 非 ERROR 的状态一律返回 `NONE`，永不重连；
2. 运维装好 `.so` 再点「开始」：`_do_start_preview` 的守卫放行 CONNECTING
   （`hik/session_actor.py:330`），然后 335 行 `_transition(START_PREVIEW)` 在
   `hik/state_machine.py` 的迁移表里查不到 `(CONNECTING, START_PREVIEW)`，
   抛 `InvalidTransitionError`；
3. 界面表现就是「每次点开始都报非法迁移」，只能重启程序。

**触发条件更正**：早先写的「首次点击开始时 SDK 库缺失」并不成立——所有 UI 启动
都经 `app/camera_manager.py:141` 先调 `_sdk_ctx.initialize()`，加载失败时异常在
那里抛出、会话仍是 DISCONNECTED，装好库再点即可正常连接。窗口内真正可能抛错的
只剩 `acquire_session` 的 `_closed` 检查，而 `sdk_ctx.close()` 只在 `main.py:118`
的 `aboutToQuit` 里、`manager.shutdown()` 之后调用，运维在 UI 上触不到。因此这是
**潜在隐患（中）**：需要 SDK 上下文关闭竞态，或将来在该窗口内新增语句才会踩到。
兜底缺口本身是真的，修法不变。

**修法**：把 253–302 行包进 try/except，异常时 `_set_error(ERROR)` 或回退
`DISCONNECTED` 再抛；状态机补 `(CONNECTING, START_PREVIEW)` 或让
`_do_start_preview` 在 CONNECTING 时先 STOP 再重连。

### R13 高：会话进入 ERROR 后没有任何恢复入口

`hik/session_actor.py:331` 在 ERROR 状态下直接
`raise RuntimeError("ERROR 状态下无法启动预览")`，而 `HikSession.reset()`
（`hik/session.py:71`）**全项目无调用方**（已 grep 确认）。监控页的「重置状态」
按钮只重置判定管线（`app/oilcheck/service.py:427` → `pipeline.reset`），不碰相机。

**复现路径**：任何一次登录失败或 `PlayM4_OpenStream/SetDecCallBackExMend/Play/
InputData` 失败都会 `_set_error(ERROR)`（均 `fatal=False`）。主界面上没有恢复入口：
监控页只区分 `previewing`/其它，ERROR 下按钮显示「开始」、点了只会再抛一次同样的错。

需要更正早先一处说法：**并非「只能重启程序」**。状态机允许 `ERROR + STOP_REQUEST`
（`hik/state_machine.py:75`），`HikSession.stop()` 会释放资源回到 DISCONNECTED；
`CameraManager._reconnect_worker`、ROI 标定对话框的 `_stop_camera`（显式接受
error 状态）、设备页禁用再启用相机（重建会话）三条路径都能复位。真正的死角是
`cameras.json` 里 `reconnect.enable=false`（UI 可关）且用户不知道去点上述任一处。

**修法**：`_do_start_preview` 在 ERROR 时先 `_do_reset()` 再继续；或
`CameraManager._start_worker` 失败时显式 `session.reset()`。

### R14 高：任何 `NONE` 决策都会清零重连退避，指数退避永远长不起来

`app/reconnect_policy.py:225-227`：`decision.action == NONE` 时无条件
`st.reset()`。而重连过程中会话必然经过 DISCONNECTED / CONNECTING（登录阻塞
可达数秒），这期间 `should_reconnect` 返回 `NONE`。

**复现**（模拟一台死相机：DISCONNECTED → CONNECTING → ERROR，tick 每秒一次）：

```
state         决策     attempt  下次重试
disconnected  None     0        -
connecting    None     0        -
error         reconnect 1        1.0 s
（循环 5 轮，延迟恒为 1.0 s）
```

`max_backoff_s=30` 形同虚设：一台断网相机每几秒就被重新登录一次并打一条
ERROR 日志。叠加 R15（空口令）还可能触发海康设备的账号锁定。

**修法**：只在「确认健康」（PREVIEWING 且活跃）时 reset 退避；对 CONNECTING /
STOPPING 这类瞬态返回 NONE 但保留 `attempt` 与 `next_attempt_ts`。

### R15 中：`env:` 引用的环境变量缺失时静默用空口令登录

`app/config_service.py:213` 的 `resolve_password` 在变量不存在时返回 `""`，
不报错也不告警（`env:` 空变量名同样返回 `""`，已实测）。

代码里的默认模板（`app/config_service.py:86`）用的正是 `env:OILCHECK_CAM_PASSWORD`。
从桌面启动器 / systemd 启动时该变量没继承 → 空口令登录 → 日志里只有
「正在连接 (用户=admin)」和海康的「用户名或密码错误」，现场会去查 IP 和账号，
联想不到是环境变量没设。

**修法**：`env:` 前缀且变量缺失/为空时抛 `ValueError`（带上变量名）或至少
WARNING；空口令直接拒绝登录，不要发给设备。

### R16 中：Actor 队列按条数限流，`DecodedData` 单条即整帧

`hik/session_actor.py:45` 的队列深度是 1000 **条消息**，而一条 `DecodedData`
就是整帧 YV12（1080p 约 3 MB）。actor 线程被阻塞的 SDK 调用（登录/登出/抓图）
占住时，两个回调线程仍往里塞：15 fps × 3 MB × 阻塞 60 s ≈ 2.7 GB。

队列满时丢的是任意一条消息（`hik/session_actor.py:528` 只按类型记日志），
`STREAMDATA` 丢块会让 PlayCtrl 收到带洞的码流，解出花屏帧直接进检测。

**修法**：给 `DecodedData` 单独用「只保留最新一帧」的槽位（等价于在回调侧
就做覆盖），`STREAMDATA` 单独限流；阻塞型 SDK 调用移出 actor 线程。

### R17 中：Actor 命令无超时等待，退出时可能钉住进程

`hik/session_actor.py:171` 的 `command.reply.result()` 没有超时；而
`app/actors/dispatcher.py:60` 的 `stop()` 只把 `_running` 置 False 并入队一个
哨兵，`_run_loop` 的 `while self._running` 在下一轮直接退出——**队列里尚未处理的
命令其 Future 永不完成**。

若此时线程池 worker 阻塞在这个 `result()` 上，`app/camera_manager.py:227` 的
`executor.shutdown(wait=True)` 会一起把进程钉在退出阶段。

**修法**：`stop()` 退出循环后 drain 队列、对每个 Command 的 reply 置异常；
`_call_command` 给 `result()` 加超时。

## 5. 事件记录与日志

### R28 高：日志的午夜轮转永久卡死，30 天保留失效

`app/logging_service.py:109-111` 用 `namer` 把轮转目标改写成
`app-<日期>.log`，而 `baseFilename` 本身已经是 `app-<启动日>.log`。

标准库 `doRollover` 取 `rolloverAt - interval` 的日期作后缀；启动当天的第一次
午夜轮转，该日期恰好等于 baseFilename 里的日期，经 namer 后目标名与
`baseFilename` **完全相同**，于是命中 `if os.path.exists(dfn): return` 直接返回
——既不关流、也不更新 `rolloverAt`，此后每次轮转都卡在同一处。

**验证**（构造与代码完全相同的 handler 参数，只比较 namer 有无）：

```
baseFilename        : app-2026-11-18.log
轮转目标（默认）     : app-2026-11-18.log.2026-11-18
轮转目标（经 namer） : app-2026-11-18.log
与 baseFilename 相同？ True
```

现场表现：程序只要连续开机超过一天，此后所有日志都堆在启动日期的那个文件里
无限增长，`backupCount=30` 的清理永不生效；[09](09-开发环境与运行.md) 承诺的
按日文件不再成立。

**修法**：不要用 namer 改写轮转目标（保留默认的 `app-<启动日>.log.<日期>`），
或改用 `delay=True` + 自建的按日命名 sink。补一条测试：推进 `rolloverAt`
跨过午夜后，断言产出了新文件且 `rolloverAt` 前进。

### R29 中：事件追加失败只记日志，内存与磁盘会不一致

`app/oilcheck/events.py:112` 的 `add` 在锁外追加 JSONL，`OSError` 只
`logger.exception` 后返回。此时事件已在内存里（UI 可见），磁盘上没有，
重启后该条事件消失。属可接受的取舍，但现场排障时容易困惑，建议在 UI 上标注
「本机事件文件写入失败」。

### R32 中：PLC 在仓库配置里默认开启

`PlcConfig` 的代码默认是 `enabled=False`（`app/oilcheck/config.py:782`），
[12](12-PLC警示灯通信与控制.md) 的示例也写 `enabled: false`，但仓库提交的

但 PLC 只允许一条 Modbus 会话（[12](12-PLC警示灯通信与控制.md) §2），现场若
博途在线监控占用端口，程序会持续刷「PLC 启动检测失败」告警；若有人顺着注释
只把 `dry_run` 关掉，就会在字节序未逐位核对前开始写 PLC。

**修法**：模板改回 `enabled: false`，并补一条针对仓库模板的断言。

### R33 中：PLC 工步配置不校验 `pick < oiling`，配置错会写出自相矛盾的位

`app/oilcheck/plc_io.py` 的 `_StepBits.from_steps` 对 `pick` 与 `oiling`
**各自**独立 clamp 到 1~8，但不检查两者的先后关系。而位语义是「VB1 = 已通过的
工步累计位、VB2 = 失败的那一步」，`pick >= oiling` 时这套语义不成立。

**复现**（同一件，先取料未涂油、再进入涂油中）：

| `steps` | 取料未涂油 | 涂油中 |
| --- | --- | --- |
| `pick=1, oiling=3`（默认，正确） | VB0=0b0010 VB1=0b0001 | VB0=0b0100 VB1=0b0011 |
| `pick=3, oiling=3` | VB0=0b1000 VB1=**0b0111** | VB0=0b0100 VB1=**0b0011**（反而变少） |
| `pick=5, oiling=2` | VB0=0b100000 VB1=**0b11111** | VB0=0b0010 VB1=0b0001 |

第二、三行里，「已通过」的位数不单调，PLC 侧按位解读会得到错误结论。

还有一个更直接的越界：`_state_step(PICKED)` 返回 `pick + 1`，而 `pick` 允许到 8，
`pick=8` 时 `VB0 = 1<<8 = 0x100`，经 `PlcFrame.hr0` 的 `& 0xFF` 后被**整个抹掉**
——PLC 看不到「取料完成」，而 UI 的 `status.frame.vb0` 仍显示 `0x100`。
实测 `pick=8, oiling=8`：`frame.vb0=0x0100`、`hr0=0xFF00`（VB0 实收 0x00）；
`pick=7, oiling=3`：取料阶段 `VB0=0x80 VB1=0x7F`，涂油中反而掉到
`VB0=0x04 VB1=0x03`，违反「同件只进不退」并抹掉 VB1 的结论位。

**修法**：`from_steps` 校验 `pick < oiling` 且 `oiling <= 7`（`_state_step(PICKED)`
要占 `pick+1` 位），不满足时回退默认并记 warning；配置加载阶段也应拒绝这种组合。


## 7. PLC 与跟踪器

### R34 严重：`_pick_plc_task` 的补报扫描方向反了，「上一件结论」永远补不出去

`app/oilcheck/service.py:945` 用 `for task in reversed(tasks)` 找 `superseded`，
但 `current` 通常就是 `tasks` 的最后一条（`_ensure_cycle` 保证同一时刻只有一条
`PROCESSING`，`active` 必然是最新那条），所以第一轮 `task.task_id == current.task_id`
就 `break`，`superseded` 恒为 `None`。

**复现**（直接调用 `_pick_plc_task`）：

| 快照 | 期望 `superseded` | 实际 |
| --- | --- | --- |
| `[TASK-1 NG, TASK-2 PROCESSING]` | TASK-1 | `None` |
| `[TASK-1 NG]`（无进行中） | — | `None`（这条本就无上一件） |
| `[TASK-1 COMPLETED, TASK-2 NG, TASK-3 PROCESSING]` | TASK-2 | `None` |

后果：连续取两件、第一件没刷完时，`OILING_MISSING` 的 NG 结论**永远写不进 PLC**，
工步从「涂油中」直接跳到新件的「取料完成」。而 `docs/12` §5.2 与
`tests/test_plc_mapper.py` 都按「能补报」编写——mapper 测试手搓证据、
`_pick_plc_task` 无任何用例，所以 `pytest` 全绿。

**修法**：只在 `current` **之前**的条目里找
（`older = [t for t in tasks if t.created_at < current.created_at]`，
再取其中最近一条非 `PROCESSING`），并补一条用真实 pipeline 连取两件的集成测试。

### R35 高：快照里没有任务时工步永久冻结

`app/oilcheck/plc_io.py:360` 在 `ev.task_id is None` 时无条件
`candidate = st.current_step`，既不看保持窗也没有超时兜底；保持窗分支只对
`current_step == FINISHED` 生效。

**复现**：在「涂油中」（VB0=0x04 VB1=0x03）时点「重置状态」
（`service.reset_station` → `pipeline.reset` 清空 `_cycles`），或示例回绕、
切换检测器触发 `pending_pipeline_reset`。之后 `t=101.2` 与 `t=3700` 的帧都是
`OILING / (0x0304, 0x0000)`，原因恒为「快照暂无任务，保持当前工步」。

现场表现：警示灯一直显示「涂油中」、良品位停在 `0b0011`，换班停线时可能整夜
如此，直到下一件到来。

**修法**：给「暂无任务」加超时回落 IDLE 并清零 VB1/VB2；`reset_station`、
`pending_pipeline_reset`、`set_station_detector_kind` 三条路径显式调
`PlcIoThread.reset()`。

### R36 高：`plc_dryrun` 回放多段视频时，第 2 段起全部帧被丢弃

`tools/plc_dryrun.py:197` 的循环只调 `mapper.reset()`，没有 `pipeline.reset()`，
而 `run_video` 每段都从 `media_ts = 0.0` 起算（第 61 行）。第 2 段第一帧
`ts=0.0 < pipeline._last_frame_ts`（第 1 段末尾），`pipeline.process` 在时间戳
倒退分支直接 return，此后每帧都倒退。

**复现**：同一 pipeline 连跑两段 100 帧——第 1 段处理 100 帧，第 2 段处理 **0** 帧、
时间戳异常计数 99。工具照常打印第二段标题。

`docs/12` §8 第 5 步正是用这个工具（默认回放全部示例视频）验收「上一件被顶掉时
补报 NG」，所以**验收会假通过**。

**修法**：循环里 `mapper.reset()` 后同时 `pipeline.reset()`；补一条「两段连放、
第二段仍产生帧」的 smoke 测试。

### R37 中：`pipeline.reset()` 让 `task_id` 重新编号，与 `hold_done_task_id` 撞车

`pipeline.reset()` 把 `_task_seq` 归零，下一件又叫 `TASK-000001`；而
`_MapperState.hold_done_task_id` 仍记着上一件的 `TASK-000001`，于是新件落进
「本件结论已报完」分支。

**复现**：某件完成且保持窗结束后点「重置状态」，新件取料帧输出
`IDLE / (0x0001, 0x0000)`，原因「本件结论已报完」——这一件在 PLC 上完全没有记录，
直到出现 `TASK-000002`。

**修法**：`task_id` 用不随 reset 归零的序号（或拼上 `cycle_id`）；或让 mapper 用
`(task_id, created_at)` 去重。

### R38 中：`plc.byte_order` 不参与写入路径，文档的 msb 回退方案无效

`PlcFrame.hr0/hr1`（`app/oilcheck/plc_io.py:121`）写死
`(vb0 & 0xFF) | ((vb1 & 0xFF) << 8)`，`PlcIoThread` 根本不接收 `byte_order`
（已 grep 确认 `plc_io.py` 中零引用）。改配置只会让
`app/oilcheck/service.py:299` 多打一条 warning，写入字节不变。

而 [12](12-PLC警示灯通信与控制.md) §3.2 明确说「若读到 `0x0100`，说明上表全部
反过来」——照做会以为已切换，实际没有。

**修法**：把 `byte_order` 传进 mapper 并在 `registers` 里交换 hi/lo；或删掉该配置项
与文档里的 msb 说法，明确本实现只支持 lsb。

### R39 中：FC16 回显校验因长度条件写错而从未执行

`app/oilcheck/plc_link.py:210` 写 `if len(body) >= 6:`，但正常 FC16 响应的 PDU
是 5 字节（`fc(1) + start(2) + count(2)`），条件恒假——注释里「确认写的确实是
这一段」的安全网从未生效。假从站正是发 5 字节
（`struct.pack(">BHH", 16, start, count)`），测试也覆盖不到。

**修法**：改成 `>= 5`。

### R40 中：ByteTrack 出生阶段的关联仍用上游硬编码 0.7，快速出现的新目标永不激活

适配器覆写了 `get_dists` 与 `_second_association`，但没有覆写
`_unconfirmed_association`——上游
（`.venv/.../ultralytics/trackers/byte_tracker.py:480`）是
`linear_assignment(dists, thresh=0.7)`。

新目标首帧 `iou_cost = 1.0`，代价 = `0.4 + 0.6·(中心距/max_center)`，要 ≤0.7
需中心距 ≤ `0.5·max_center`。以 `max_distance=0.15` 计（1000×1000 画面对角线
约 1414px，`max_center≈212px`），中心距需 ≤106px/帧。4fps 抽帧或 1920 宽画面
门槛更高时，手快速伸入可能整段不被跟踪。

模块 docstring 第 21–22 行「`match_thresh=1.0` 表示只看距离门限」在出生阶段不成立。

**修法**：覆写 `_unconfirmed_association`，把 0.7 换成 `self.args.match_thresh`。

### R41 中：满员淘汰会把正在匹配的轨迹逐出并永久退役

`app/oilcheck/bytetrack_adapter.py:530` 用
`max(key=lambda t: (not t.matched, t.missing_s))` 选牺牲者；全部轨迹都 `matched`
时键全是 `(False, 0.0)`，`max` 返回第一个元素——正在被检测到的老轨迹，随后被
`_retire`（永不复活）。

**复现**：`max_active=2`、每帧 3 个稳定检测 → ID 序列 `[2,3] → [3,4] → [4,5]`，
逐帧轮换，退役集合持续增长。现场手部 `max_active=8`、刷头 4，误检多时可能触顶，
被淘汰的恰是业务在用的那只手，`_visits` / `hand_track_id` 关联随之断裂。

**修法**：满员且全部 `matched` 时直接拒绝新轨迹；只在存在未匹配轨迹时淘汰，
victim 按 `last_seen_ts` 确定性选取。

### R42 中：设置页「测试连接」与写入线程抢 PLC 唯一会话

`ui/pages/settings_page.py:384` 自建 `PlcLink` 连同一台 PLC。`dry_run=false` 时
`PlcIoThread` 写完不关 socket，靠 `refresh_interval_s=1s` 的重写保活
（[12](12-PLC警示灯通信与控制.md) §5.8 的设计）。第二条连接按 §2 的实测会 SYN
超时，于是「测试连接」在生产模式下必然失败，提示还会把现场引向「检查博途在线
监控」——真正占着会话的是本程序的写线程。

**修法**：改走 service，让 `PlcIoThread.check_connection()` 在锁内先关自己的 link
再探测；或探测前停线程、探测后重启。提示文案要写明这一可能。

### R43 中：`plc_check.py` 的 VB0 解读表只有 0~2 三个键，第 4 位会 KeyError

`tools/plc_check.py:83` 的 `VB0_STEP_HINT[bit] for bit in range(4)` 用例中，
`VB0_STEP_HINT` 只有 0~2 三个键；VB0 第 4 位（`0x08`）会抛 `KeyError: 3`
——偏偏在现场数据「不像本方案写的」时最需要这个工具的时候崩掉。

### R47 高：只处理 SIGINT，SIGTERM/SIGHUP 硬杀会丢掉整个未收尾录制分段

`main.py:91-95` 只注册了 `signal.SIGINT`。现场用 `kill`、`systemd stop`、关闭
SSH 终端（SIGHUP）终止进程时，`_cleanup` / `oil_service.shutdown()` /
`recorder.stop()` 全部不执行。

**复现**（仓库自带 `TrainingRecorder`、`opencv-python 5.0.0.93`、mp4v、
`segment_seconds=300`，写 46 帧后 `SIGTERM`）：

```
产出 mp4: cam1_20261118_202027.mp4
  size: 44 bytes
  isOpened(): False        (moov atom not found)
  readable frames: 0
  sidecar: status=recording frame_count=0
manifest 存在: False 行数: 0
```

丢的是**整个未收尾分段**（默认最多 300 s 训练视频），不是最近几帧；且
`_append_manifest` 只在 `_finalize_segment` 里执行，所以 manifest 也没有条目，
事后无法从清单定位。`docs/07:162` 排障表「视频仍可播放，用 manifest/文件名恢复
时间」在硬杀路径下是错的。

**修法**：同时注册 `SIGTERM`（可行时含 `SIGHUP`）到同一个处理函数，让
`app.quit()` 走 `aboutToQuit` → `_cleanup` → `recorder.stop()` → `writer.release()`；
并修正 `docs/07` 的排障描述。

### R48 高：录制器不按 `recording.fps` 限流，成片时间轴失真

`app/oilcheck/recorder.py:184` 的 `submit` 直接入队，`_write_frame` 直接
`writer.write`，`fps` 只写进了 `VideoWriter` 构造与元数据。而服务层每个新帧都
`recorder.submit`（`app/oilcheck/service.py:746`），且轮询节拍取
`max(pipeline.max_fps, recording.fps)`。

**复现**：15 fps 源、以 30 Hz 提交、`recording.fps=15`，喂 3.0 秒 → 写出 56 帧
→ 成片 `56/15 = 3.73 s`。写盘够快时是 2 倍速，写盘跟不上时队列丢帧、倍率变小，
但**时间轴必然失真**，训练素材的动作速度不再等于真实速度。

**修法**：在 `_write_frame` 前按 `ts - last_written_ts < 1/fps` 丢弃并计入
`_frames_dropped`。

### R49 高：配置文件不是 UTF-8 时启动崩溃且无任何提示

`app/config_service.py:142`（以及 `:161`、`app/oilcheck/config.py:1954`）用
`open(encoding="utf-8")`，而 `except (OSError, json.JSONDecodeError)` **不覆盖
`UnicodeDecodeError`**（它是 `ValueError` 子类）。

**复现**（`OILCHECK_CONFIG_ROOT` 指向临时目录，`app.json` 按 GBK 写入含中文字段）：
`load_app_config()` 抛 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbd`。
该调用在 `main.py:29`，早于 `main.py:33` 的 `setup_logging`——Windows 双击运行时
没有控制台，用户看到的是「窗口闪一下就没了」，日志目录里也没有记录。

中文 Windows 记事本「另存为 ANSI」正是 GBK，而配置文件里本来就有大量中文注释与
工位名，这个操作很自然。

**修法**：统一用 `read_bytes()` + 依次尝试 `utf-8-sig` / `gb18030` 解码；异常
捕获补成 `(OSError, ValueError)`。

### R50 高：同一帧被 `_record_outside_holding` 记录 2~3 次，投票窗口被单帧灌满

`app/oilcheck/pipeline.py` 有三处调用 `_record_outside_holding`
（`:856` 轨迹新建、`:878` 采样点、`:935` 未确认进盘）。它们看似互斥，但实测同一
`ts` 会被调用 **3 次**。

**复现**（包一层 spy 统计每个 `ts` 的调用次数，空手在盘外走 20 帧）：
总调用 31 次覆盖 20 帧，分布 `{1, 2, 3}`，第一帧 3 次、之后多数帧 2 次。

后果：`pick_history_samples` 默认 3，一帧就能把窗口灌满，
`_mostly_empty_outside` 的多数票退化成「单帧随机数」——一次噪声观测即可把真实
取料判成「带料进盘」而整件丢掉（或反之）。

**修法**：在同一帧内只记录一次（用 `_last_recorded_ts[hand_id]` 去重，或把三处
调用合并为单一入口）。

### R51 高：`_screw_static` 只与单一参考帧比对，那一帧漏检即整段失效

`app/oilcheck/pipeline.py:1091` 取 `self._screw_history[-8]` 的**单帧**位置比对
IoU。若参考帧恰好漏检该杆，位置从未变动的杆会被判成「在动」。

影响面比「整段 8 帧」窄（每帧的 `[-8]` 都指向不同的历史帧，只有一个漏检帧会
恰好回指到它），但后果不轻：一旦锚点借此捕获了静置杆，`_static_anchor_ok` 的
「锚点 ±0.02 同根」例外（`:1491-1500`）会让它一直合法，之后刷真杆的接触时长
不再累计 → 漏涂 NG。同一漏洞还影响 `_screw_parked_in_tray`（进盘定性）与
`_carrying_out_of_tray`。

**修法**：改为在窗口内命中 ≥K 帧才判静置，并跳过该杆漏检的参考帧。

### R52 中：`clear()` 与 `add()` 不在同一临界区，「清空事件」会留下磁盘残留

`app/oilcheck/events.py:152` 的 `clear()` 在锁内 unlink 文件，而 `add()`
（`:110-112`）与 `submit_review()` 是**锁外**追加。

**复现**（在 `_append_jsonl` 前插 0.15 s 延迟放大窗口，`clear()` 后 join）：
`removed=1`、内存 0 条，但 `events-*.jsonl` 仍有 1 行——清空后磁盘残留该事件。
`_btn_clear` 不受运行状态限制，生产运行中可触发。

（早先声称的「反向时序会写进已删 inode 导致内存有、盘上没有」不成立：能先 open
就说明内存写入早于 clear，必被清掉。）

**修法**：把「清内存 + 删文件」与追加放进同一把锁，或按天文件做代际标记。

### R53 中：`start_training_recording` 忽略 `recorder.start()` 的 `False`

`app/oilcheck/service.py:615` 丢弃返回值，`ui/pages/recording_page.py:419-427`
也无条件弹「已开始录制」。

可达路径：`stop()` 的 `join(timeout=5.0)` 超时（写盘卡在慢盘/满盘/不可中断 IO），
此时 `_active=False` 但 `_thread` 仍存活，再点开始会被 `recorder.py:142-144` 拒绝。

后果：不抛异常、不打日志、`_last_error` 为空，UI 先弹 2 秒「已开始录制」，紧接着
`_refresh_status` 又显示「未开始」，自相矛盾；操作员要自己察觉这次没录上。

**修法**：`start()` 返回 False 时抛异常或写 `last_error` 并记 warning。

### R54 中：`reload()` 静默丢弃进行中的作业周期

`app/oilcheck/service.py:196` 的 `reload()` 用全新 `StationPipeline` 整体替换
运行时，进行中的周期（`_cycles`）直接消失，不发任何 NG 或「中断」事件，
`_task_seq` 也归零。

**复现**：周期处于 `PICKED`（PICK 已入库）时点「保存全部」→ reload 后
`_cycles=[]`、事件仍是 1 条——这一件的漏涂永远进不了复核页；下一件又叫
`TASK-000001`，而 `cycle_id` 不变（事件按 `cycle_id + task_id` 追溯会撞车）。
同时 PLC 线程被重建，保持窗与 `hold_done_task_id` 一并丢失（叠加 R37）。

**修法**：reload 前先结算活动周期（走 `_supersede_unfinished` 或发「配置重载
中断」事件）；`_task_seq` 提到 service 层或拼上重建序号。

## 9. 复核中被推翻的推断

记录在此以免后续重复排查：

- **⚠ 撤销本报告早先的一条错误结论：「SIGTERM 不会留下不可播放的 MP4」**。
  早先的实验用 `del writer` 触发 GC，那是**正常解释器退出**路径，OpenCV 会在
  析构时写 moov。用仓库自带 `TrainingRecorder` + `kill -TERM` 实测
  （`opencv-python 5.0.0.93`、mp4v、`segment_seconds=300`）：分段 mp4 只剩
  **44 字节**、`cv2.VideoCapture.isOpened()` 为 `False`、`moov atom not found`、
  sidecar 停在 `status=recording, frame_count=0`、`manifest.jsonl` 无条目。
  丢的是**整个未收尾分段**（默认最多 5 分钟）而非几帧。`docs/07:162`
  「视频仍可播放」在硬杀路径下是错的。该条已升格为 R47。

- **`brush_hold_s=0` 不会「单帧即判涂油完成」**。第一帧只建立 `last_brush_ts`，
  累计从第二帧起；实测 0.0 与 0.2 在 2 帧时行为相同。NaN 被夹成 0 的真实后果
  是「两帧接触即完成」，仍是错误判定，但不是单帧即过。

- **「录制侧没有磁盘保护、与 docs/07 矛盾」——表述需修正**。`docs/07:153`
  那句写在「建议」列表里，不是承诺；录制线程在写盘失败后确实会退出
  （`app/oilcheck/recorder.py:228-256`），但目前没有任何磁盘余量检查，属**未实现**而非矛盾。

- **`_sync_keys` 启动补键不会覆盖现场值**：只补缺失键、不改已有值，实测连跑
  三次文件字节不变。

- **`FrameBuffer` 的并发读写是安全的**：`get()` 返回不可变 `Frame` 快照，
  BGR 每帧新建、无人原地改写，UI 与检测并发读同一 ndarray 不会撕裂。

- **PLC 的保持窗语义正确**：新件到来时仍维持工步 4，窗结束后回工步 1 并清零；
  写失败时 `_on_write_error` 关连接并把 `last_written` 置 None，重连后立即重写
  完整帧，不会静默停在旧工步。

- **切换示例视频的重置顺序是安全的**：`set_station_video` 先置
  `pending_pipeline_reset=False` 再 `submit(pipeline.reset)`，两次重置都排在
  同一执行器线程之后，不会互相吞掉。

- **`_gap_samples` 不会被时间倒退污染**：`app/oilcheck/pipeline.py:459` 的守卫先丢弃倒退帧，
  注入 -5s 后 `frame_scale` 与中位数均未变化。

## 10. 做得好的地方

这些设计有针对性，改动时注意不要破坏：

- **PLC 链路**：用真实 socket 假从站做端到端测试（`tests/test_plc_io_integration.py`），
  FC16 字节序、VB0/VB1/VB2 位映射、200 ms 轮询可能跨过终态帧时的「补报上一件」
  都有对应实现与测试。
- **示例回放**：媒体时间用累计交付帧数计算，回绕与变速都不会让时间倒退；
  取帧改成小容量队列「每帧只消费一次」，解决了轮询相位造成的漏帧。
- **海康 SDK 封装**：`NET_DVR_*` 的错误信息取用（`last_error_detail` 按平台选
  gbk/utf-8）、`wait_for_idle` 同时等待会话租约与 actor 退出、登录失败释放租约、
  `_do_stop` 的 `StopRealPlay → PlayM4_Stop/CloseStream/FreePort → Logout` 顺序
  与句柄置 -1、回调对象保存在实例上不会被 GC——这些都是这类项目的高发坑。
  唯一的例外就是 R11 的截图签名。
- **判定参数设计**：纯时间阈值不随帧率缩放、距离门限按帧间隔放大，取向正确。
- **配置写入**：`mkstemp` + `fsync` + `replace` 的原子写；未知键只提示不删除，
  兼容新旧版本交替运行。
- **安全默认值**：`tools/plc_check.py` 的写探测需显式 `--allow-write-probe`；
  `tools/plc_dryrun.py` 完全不连 PLC；`tools/diagnose_replay.py` 不触发配置迁移。
